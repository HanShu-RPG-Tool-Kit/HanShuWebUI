# `.tts` 规范方案(角色配音方案)

定义 `meta/voice/<角色名>.tts` 的格式。**一个文件 = 一个角色的配音方案**,文件名即角色名
(`旁白.tts` → 角色「旁白」)。于是"角色 → 音色"的映射不是一张配置表,而是文件系统本身:
加一个角色加一个文件,改一个角色改一个文件。

> 工程里还有**第二类配音配置**:`meta/voice/service/<服务名>.ttsservice`(TTS 服务定义)。
> 它讲的是"用哪个账号、哪个端点、哪个模型",是工程级而非角色级。见 §4。

**前提:`.tts` 由应用写,不由用户写。** 用户在可视化编辑器里改配置,不打开这个文件。
三条取舍原则由此推出:

1. **一个概念只留一种写法。** 不给人写便利的糖 —— 糖会带来"两种合法输入"与优先级歧义。
2. **凡能自动决定的,一律不写进文件。** 协议差异、章节上限、输出格式都是实现细节。
   "隐藏配置细节"不是靠编辑器藏,是靠**文件里根本没有**。
3. **没有继承,没有兜底,没有覆盖。** 不设顶层默认值 + 逐项覆盖这类机制 ——
   它们让"这个值到底是什么"要靠优先级去推。重复可以接受:**文件没有人类读者**,
   便利应该长在编辑器上("应用到所有语言"),而不是长在格式里。

### 本文管什么、不管什么

| 管 | 不管 |
|---|---|
| 用哪个服务 / 端点 / 模型 | **密钥本身** —— 只放引用,真实值在本机凭据库 |
| 每个语言的音色来源(预置音色 / 克隆) | **哪一段用 TTS、哪一段用真人录音** —— 那是录音棚的操作 |
| 语速 | **情绪 / 风格** —— 那是录音级的操作,不是音色级的属性 |
| 服务的连接形态与能力开关 | **请求怎么发** —— 适配器的事,不落盘 |
| 样本放哪、随不随工程走(config 只管引用) | **样本怎么分享、工程给谁** —— 工程持有者的事 |

下面两条是**否定性边界**,值得说明理由:它们都属于**一次具体的演绎**,
而 `.tts` 描述的是**音色**。同一份音色可以念快念慢、可以平静可以激动 ——
那些随段落走,绑在音色上就错了。

最后一行也要说清:**规范只负责把样本"指到"某个 assets 路径,以及让它随工程一起走**
(§5.6)。至于"这份工程要不要给别人、给了别人会怎样",那是持有者的判断 ——
编辑器不替他做决定,也不替他兜底。

## 1. 配置分层

配置分四层。切分原则只有一条:

> **决定"合成出什么"的配置,跟着工程走;凭据不跟工程走。**

同一份剧本 + 同一份角色方案,在任何机器上应该合成出**一样的声音** ——
端点和模型决定这件事,所以它们必须随工程;密钥不决定这件事,所以它不随工程。

| 层 | 内容 | 存哪 | 作用域 |
|---|---|---|---|
| **工程服务** | 供应商 / 协议 / 端点 / 模型 / 能力开关 / 凭据**引用** | `meta/voice/service/<服务名>.ttsservice` | 工程 |
| **角色方案** | 服务引用 / 音色来源 / 语速 | `meta/voice/<角色>.tts` | 角色 |
| **凭据** | 真实的密钥 | 应用凭据库 | 机器 |
| **系统** | 输出格式 / 文本切分 / 字符上限 / 单声道 Vorbis | **不落盘** | — |

### 服务定义为什么是独立文件,而不是角色的内联字段

- 一个工程里通常只有 1–2 个 TTS 账号,却有几十个角色。内联意味着同一份端点信息
  在几十个文件里重复,**改一次端点要改几十处**。
- 内联会逼出一个荒谬的界面:每建一个角色,都要用户再填一遍 API 地址。
- 服务是**工程级**概念,角色是**角色级**概念。两者生命周期不同:删掉一个角色
  不该影响服务;换一个端点不该动任何角色文件。

独立成文件后,`.tts` 的**每条语言条目**只写 `service: "minimax-main"` ——
一个**工程内**的引用,不再是悬空 id。文件落在 `meta/voice/service/`,理由见 §8。

### 为什么凭据不跟着工程走

服务定义里有 `auth`,但里面**只有引用**(`env:XXX` / `app:XXX`),没有密钥。

**工程是注定要出去的**(会给人、会上传、会备份),所以明文密钥写进去就等于泄漏。
这不是假设,是三条已经存在的路径:

| 路径 | 机制 | 后果 |
|---|---|---|
| **导出工程包** | `projectPack` 遍历包内全部文本文件 | `.ttsservice` 被原样打进出厂包 |
| **Agent 读取** | `read_source` 按逻辑名读**任意包内文件**,`meta/` 不在排除之列 | 密钥被拼进模型请求 |
| **进版本库 / 发出去** | 工程目录进了 git 或给了别人 | 进了 git 历史就**删不掉**,只能作废重签 |

所以"把密钥写进文件"**不是少做一步,而是同一件事要在三处各排除一遍** ——
排除出工程包、排除出 Agent 的可见范围、排除出版本库。三处都得记得,漏一处就泄漏。
`*Ref` 只需要记住一次:**密钥不存在于任何文本里。**

协作者拿到工程后,看到的是"这个工程需要一个叫 `OPENAI_API_KEY` 的凭据"
(§7.2 的凭据体检会列成待填清单),自己填一份即可。这一步无论如何都省不掉 ——
把密钥写进文件并不能免掉它,只是把"自己填一份"换成"把我这份复制过去"。
所以把服务定义放进工程**不增加**协作成本,反而省掉了"该配哪家、端点填什么、用哪个模型"的猜测。

## 2. 格式:JSON

`.tts` 用 JSON,与 `.lang` / `.voice` 对齐:

- 仓库现有配置格式全是 JSON,没有 YAML。
- 应用级设置已是 `localStorage` + `JSON.parse`。
- 解析用 `JSON.parse`,写出复用 `.voice` 的保真写入思路 —— **依赖零新增**。
- 文件由应用生成,缩进与引号由生成器保证,不存在手写 YAML 的缩进风险。

代价是没有注释位。可以接受:**这个文件没有人类读者** —— 它的"注释"是编辑器里的标签与说明。

## 3. 示例

**除 §5 标注「必需」的键外,其余都可省略。**

**顶层只有 `version` 与 `voices` 两个键。** 语言之外没有第三个层级 —— 所有配置都落在语言条目里。

### 3.1 最小形态

`meta/voice/旁白.tts` —— 一条语言就是最小形态,没有更短的了。

```json
{
  "version": 1,
  "voices": {
    "zh_cn": { "service": "openai-main", "voice": "alloy" }
  }
}
```

### 3.2 多语言:每条语言自成一体

```json
{
  "version": 1,
  "voices": {
    "zh_cn": { "service": "minimax-main", "voice": "linwan_v1" },
    "en_us": { "service": "elevenlabs-main", "voice": "3l6LtJBhYtUmpJmHnMwv" },
    "ja_jp": {
      "service": "elevenlabs-main",
      "voice": "3l6LtJBhYtUmpJmHnMwv",
      "speed": 1.05
    }
  }
}
```

**中文用 MiniMax、英文用 ElevenLabs** 是真实存在的取舍(前者中文听感更好,后者多语言更强)。
所以 `service` 属于语言条目 —— 每条都写全,**没有顶层默认值可以省**。

看起来重复,但重复只发生在文件里:用户从不打开这个文件,编辑器负责区分"改这一条"与
"改所有语言"。详见 §5.5。

> `speed` 不必每条都写。不写的条目用 `1.0` —— 那是**字段默认值**,不是从其它语言继承来的。
> 上面只有 `ja_jp` 写了 `1.05`,因为它确实要快一点。

### 3.3 逐语言克隆

```json
{
  "version": 1,
  "voices": {
    "zh_cn": { "service": "minimax-main", "voice": "linwan_v1" },
    "en_us": { "service": "elevenlabs-main", "voice": "3l6LtJBhYtUmpJmHnMwv" },
    "ja_jp": {
      "service": "elevenlabs-main",
      "clone": {
        "samples": ["assets/voice-samples/林晚/ja_jp/01.wav"],
        "consent": "meta/docs/声音授权-林晚-ja_jp.md"
      }
    }
  }
}
```

每个语言的音色来源**二选一**:预置音色给 `voice`,克隆给 `clone`。

逐语言克隆对应的是真实情况:**中文配音员和英文配音员是两个人,授权书也是两份。**

样本与授权书**按类型分家**:样本是二进制,归 `assets/` 的资源系统管;
授权书是文本创作资料,归 `meta/docs/`。两条路径各自由已有的机制负责。

## 4. 服务定义(工程文件)

### 4.1 先分清两件事

```
`.tts`：  voices["zh_cn"].service = "minimax-main"     ← id 字符串
                    │
                    │  在工程内解析
                    ▼
磁盘上：  meta/voice/service/minimax-main.ttsservice
```

**`.tts` 里的 `service` 永远是一个 id 字符串,不内联。** 它解析到
`meta/voice/service/<id>.ttsservice` —— 一个**工程内**的文件,不是别处的一张表。

放在 `meta/voice/` 底下,是因为**服务定义只服务于 TTS**;理由见 §8。

要有这一层,是因为**服务是工程级概念**:一个工程通常只有 1–2 个 TTS 账号,
却有几十个角色。内联意味着同一份端点信息在几十个文件里重复,改一次端点要改几十处;
而且会逼出一个荒谬的界面 —— 每建一个角色,都要用户再填一遍 API 地址。

用哪个服务由 `voices.<k>.service` 表达(见 §5.5),不需要内联整份定义。

### 4.2 文件形状

`meta/voice/service/minimax-main.ttsservice`

```jsonc
{
  "version": 1,
  "label": "MiniMax 主账号",               // 可省：界面显示名，默认取文件名
  "provider": "minimax",                   // 预设档：决定协议与一堆默认值
  "auth": { "apiKeyRef": "env:MINIMAX_API_KEY" },
  "baseUrl": "https://api.minimax.io/v1",  // 可省：预设给默认
  "model": "speech-2.8-hd",                // 可省：预设给默认
  "capabilities": ["clone"]                // 可省：只能在预设范围内收窄
}
```

**没有 `id` 字段。文件名就是 id** —— 与 §5.1 对角色名的处理是同一条规则:
名字只有一个来源,否则就会出现"文件名与内部 id 不一致"的合法输入,引用没法静态解析。
详见 §4.7。

三个轴,各回答一个问题,互不替代:

| 轴 | 回答 | 例 |
|---|---|---|
| `provider` | **走哪个预设?** | `minimax` / `openai` / `elevenlabs` / 用户自建预设 / `template`(= 不走预设) |
| `protocol` | **怎么发请求?** | `openai-compatible` / `elevenlabs` / `azure` … |
| `auth` | **凭什么发?** | 凭据引用 |

`provider` 单独成轴,是因为**同一协议下不同厂商的差异是真实的**:
官方 OpenAI 与 Groq 都是 `openai-compatible`,但可用的模型、音色、能力完全不同。
把厂商信息折进 `baseUrl` 就丢掉了这些语义。

### 4.3 `provider`:预设档

**`provider` 是预设表的键。** 每个预设档提供:

- `protocol` —— **固定**,不可覆盖
- `baseUrl` / `model` 的默认值(留空表示该预设**没有**默认端点,服务必须自己填)
- 协议**提供**的能力(上限)
- **默认开启**的能力(⊆ 上一项)
- 音色来源(固定枚举,还是调列表接口;留空即不静态校验)
- 在该协议下语法合法的模型名候选(留空即不限定)

| `provider` | 固定协议 | 协议提供的能力 | 默认开启 |
|---|---|---|---|
| `openai` | `openai-compatible` | `clone`(需 sales 审批) | — |
| `elevenlabs` | `elevenlabs` | `clone` | `clone` |
| `minimax` | `minimax` | `clone` | `clone` |
| `azure` | `azure` | `clone`(Limited Access) | — |
| `google` | `google` | — | — |
| `polly` | `polly` | — | — |
| `groq` / `openrouter` / … | `openai-compatible` | — | — |
| **`template`** | **由用户填** | 取决于选中的协议 | — |

> **"协议提供"与"默认开启"是两件事,不能合成一个集合。**
> `.ttsservice` 的 `capabilities` 只能从**协议提供**那一列收窄;不写 `capabilities` 时
> 取的是**默认开启**那一列。合成一个集合会让"协议提供但默认关闭"变成"用户永远开不了"
> —— 那正是 Azure 与 OpenAI 的情况(§5.6)。

> 最后一行 `template` **不是预设条目**,所以它**不在这张预设表里**(见 §4.4)。
> 上面几行才是表的内容 —— 内置预设 + 用户自建预设。

#### 预设表是**插件式**的

**预设表是数据,不是代码分支。** 加一家供应商 = 加一条数据 —— 不需要发版、
不需要新写适配器(只要它的协议已在枚举里)。这是本方案真正的扩展点。

而且**用户可以自己往表里加条目**:填一次 {名字 / 固定协议 / 默认端点 / 默认模型 /
能力 / 凭据形态},它就变成一个与内置预设**完全等价**的 `provider`,之后建服务时随手可选。

- **没有 `custom` 这个档位。** "自定义"在此处的语义就是**自定义预设** ——
  它已经由"往表里加一条"表达了,再设一个 `provider: "custom"` 是把同一件事说两遍。
- 用户自建的预设与内置预设**同权**:校验、编辑器、能力约束走同一条路径,
  不存在"只有内置才能怎样"的分支。
- 内置预设随应用更新增补;**用户自建的预设不跟版本走**,存在应用级存储里。
- **自建预设的键不得与内置预设重名**,重名判非法(不设"谁覆盖谁"的优先级,
  与 §前提 第 3 条一致)。

这条决定了编辑器的形态:预设管理不是一张只读表,而是一个**可增删的列表**。

### 4.4 `provider: "template"`:一次性连接

预设表里没有、也不值得单独建一条预设时(自建网关、临时中转):

```jsonc
// meta/voice/service/my-gateway.ttsservice
{
  "version": 1,
  "label": "自建网关",
  "provider": "template",
  "protocol": "openai-compatible",     // template 时**必填**
  "auth": { "apiKeyRef": "app:my-gw-key" },
  "baseUrl": "https://tts.internal/v1" // template 时**必填**
}
```

`protocol` 取值来自 §5.2 的枚举。

**它不写进预设表。** `template` 与预设档的唯一区别是:**预设固定协议,`template` 由用户选协议。**
所以判断标准很直接 —— 这个连接以后还会再建第二个吗?会,就建一条预设;只有这一个,
就用 `template`。

> **两个名字都不在别处复用:**
> 预设表里没有 `custom`(自定义预设 = 往表里加一条),协议枚举里没有 `template`
> (协议是"怎么发请求"的客观形态,不存在"自定义协议")。一个概念只留一种写法。

### 4.5 `auth`:凭据

**这是唯一真正需要嵌套的地方** —— 因为不同协议的凭据形态本来就不一样:

```jsonc
// 单值型：OpenAI / ElevenLabs / MiniMax / Azure
"auth": { "apiKeyRef": "env:MINIMAX_API_KEY" }

// Polly 的 SigV4 需要一对密钥
"auth": { "accessKeyRef": "env:AWS_AK", "secretKeyRef": "env:AWS_SK" }

// Google 用 service account
"auth": { "serviceAccountRef": "app:gcp-sa" }
```

预设档决定该协议要哪种形态,编辑器据此渲染对应的表单 —— 用户看到的是
"贴一个 Key"或"贴一对 Key",不是抽象的字段名。

除 `auth` 外**不再往下嵌套**:`baseUrl` / `model` 单层就够,再分一层只是多敲字。

### 4.6 预设档的覆盖规则

| 字段 | 预设时 | `template` 时 |
|---|---|---|
| `version` | 必填,必须为 `1` | 同 |
| `label` | 可省(默认取文件名) | 同 |
| `provider` | 必填(内置预设 ∪ 用户自建预设) | `"template"` |
| `protocol` | **派生**。可省;写了必须与预设一致,否则判非法 | **必填** |
| `baseUrl` | 可省(用预设默认),**可覆盖** | **必填** |
| `model` | 可省(用预设默认),**可覆盖** | 可省 |
| `auth` | 必填 | 必填 |
| `capabilities` | 可省,**只能收窄,不能放宽** | 可省,同规则 |

两条关键规则:

- **`protocol` 是派生值,不是输入值。** 预设时写了也只允许与预设一致 ——
  否则会出现 `provider: "openai"` + `protocol: "azure"` 这种自相矛盾的合法输入。
- **`capabilities` 只能收窄。** `capabilities ⊆ 预设「协议提供的能力」`。用户可以把
  `clone` 从 ElevenLabs 的服务上**去掉**(比如账号没开通),也可以在 Azure 的服务上**加上**
  (拿到 Limited Access 之后),但**不能**在 Google 的服务上加上 —— 协议不提供的能力开不出来。
  这正是"克隆由服务商约束"的落地形式(见 §5.6)。注意上限是"协议提供"那一列,
  不是"默认开启"那一列,否则 Azure / OpenAI 的能力就永远开不了。

> **这里的"预设默认"和 §5.5 禁掉的"顶层默认值"不是一回事。**
> 预设档的默认是**推导出来的** —— 选了 `provider: "minimax"`,端点和模型就唯一确定了,
> 写不写都一样,所以省掉它**不产生歧义**。而顶层 `service` 是**并列一个默认值**,
> 没有任何东西能推出它来,只会让读取方多找一处、多一层优先级。
> 判据是:**这个值能不能从已选项唯一确定?** 能 → 可以省;不能 → 必须写。

**没有 `extra` 这类"透传口袋"。** 留一个万能字段的代价是:没人知道该往里放什么,
也没人知道校验器要不要管它。将来真需要开协议私有选项(比如情绪 / 风格那一类,
它们现在明确不做),就按 §前提 第 1 条新开一个**有名字、有类型、有校验**的字段,
而不是先塞进一个袋子。

### 4.7 文件名(id)与 `label`

- **文件名去 `.ttsservice` 即 id**,命名规则与其它资源名一致(`normalizeResourceName`):
  非空,不含 `/\:*?"<>|`,后缀在白名单里;**允许中文**(与 `序章.hs` 一致)。
- **id 被 `.tts` 引用,所以创建后不宜改。** 用户改显示名只改 `label`。
- 但文件可以被手动改名 —— 与角色不同,**服务是被引用的,改名会断链**。
  所以应用里的"重命名服务"**自动改写所有引用它的 `.tts`**;
  绕过应用直接改文件名,则由 §7.2 的语义校验报"引用了不存在的服务"。
- 同一个 `provider` 可以建**多个服务**(主账号 / 备用账号 / 不同区域)。
  所以 id 与 `provider` 无关,不能拿 `provider` 当键。

### 4.8 "创建服务"实际创建了什么

用户点"新建服务 → 选 MiniMax → 贴 API Key",应用做两件事,分别落到两处:

```
①  meta/voice/service/minimax-main.ttsservice
        └─ 进工程：provider / 端点 / 模型 / 能力 / 凭据"引用"

②  本机凭据库 → env:MINIMAX_API_KEY
        └─ 不进工程：真实的密钥
```

这一步的分工正是 §1 那条切分原则的具体形态:**决定"合成出什么"的进工程,
决定"你凭什么用"的留在本机。** 于是工程可以被完整分享,而密钥一次也不会泄漏。

## 5. 字段规则

### 5.1 角色名(来自文件名)

文件名去掉 `.tts` 就是角色名,必须与剧本里的**说话人名**一致
(`.hs` 里的 `旁白:……//` 这种行首 `名字:`)。

- 允许中文(项目其余部分同样允许中文文件名,如 `序章.hs`)。
- 不得包含 `/ \ : * ? " < > |`(沿用 `normalizeResourceName` 的校验)。
- **顶层不接受 `character` / `name` 之类的名字字段** —— 写了会报错。名字只有一个来源,
  否则会出现"文件名与内部名字不一致"的合法输入,映射就没法静态判定了。
- 角色改名 = 文件改名。文件名就是映射键,**改名天然不会留下断链**。

### 5.2 协议枚举(定义在应用层)

`protocol` 只能取以下值,适配层按它分派。预设档带出它(不可改),
只有 `provider: "template"` 时才需要用户选:

| 值 | 对应 | 端点形态 | 语言码字段 |
|---|---|---|---|
| `openai-compatible` | OpenAI、Groq、OpenRouter、各类自建网关 | `POST /v1/audio/speech`,JSON → 裸音频字节 | **无**(按正文自动判语言) |
| `elevenlabs` | ElevenLabs | `POST /v1/text-to-speech/{voice_id}`,JSON → 裸音频字节 | `language_code`,ISO 639-1(`zh` / `ja`) |
| `azure` | Azure Speech | `POST /cognitiveservices/v1`,**SSML** → 裸音频字节 | SSML `xml:lang`,BCP-47(`zh-CN`) |
| `minimax` | MiniMax | `POST /v1/t2a_v2`,JSON → **JSON 内 base64** | **无** |
| `google` | Google Cloud TTS | `text:synthesize`,JSON → JSON 内 base64 | `languageCode`,BCP-47 |
| `polly` | Amazon Polly | `SynthesizeSpeech`,SigV4 签名 | `LanguageCode` |

**协议枚举保持封闭。** 它是代码分支的入口 —— 每个值背后是一个适配器,
所以只能在发版时增加。**扩展点不在这里,在 `provider` 预设表**(见 §4.3):
只要协议已在枚举里,加一家新供应商是纯数据改动。

> 枚举里**没有"自定义协议"这一项**。协议是"请求长什么样"的客观事实,
> 不是用户可以发明的 —— 要接一个没见过的协议,只能加进枚举(发版)。
> 用户能自由决定的只有"用哪家 + 端点填什么",那就是 `provider` 的 `template` 档(见 §4.4)。

> `elevenlabs` 单列而不并进 OpenAI 兼容:它的 `voice` 在 **URL 路径**里,
> 鉴权用 `xi-api-key` 头而非 `Authorization: Bearer`,请求体键名也不同(`text` 而非 `input`)。
> 硬塞需要一层路径 + 键名 + 鉴权头的特例改写,单列一个薄适配器更干净。

### 5.3 凭据引用(硬规则)

`auth` 里**每一个 `*Ref` 字段**都必须匹配 `^(env|app):[A-Za-z0-9_.-]+$`:

- `env:ELEVENLABS_API_KEY` —— 从环境变量取
- `app:minimax-key` —— 从应用级凭据库取

规则不做字段名白名单,而是**按后缀识别**:任何以 `Ref` 结尾的键都是凭据引用。
这样 `auth` 将来加新形态(比如 Polly 的 `secretKeyRef`)不用改校验器。

**任何其他形式一律判非法。** `auth` 是唯一能出现凭据的地方,而它只放引用。

服务定义文件**会进工程**,而工程会给人、会上传、会备份(三条具体路径见 §1)。
所以它同样只放引用:`env:` 指向协作者自己的环境变量,`app:` 指向他自己的凭据库。
**密钥永远不进任何文本。**

### 5.4 `service`(在每个语言条目里)

**必需**,字符串,必须能解析到工程内的 `meta/voice/service/<id>.ttsservice`
(文件名去后缀即 id)。

- 命名规则与其它资源名一致(`normalizeResourceName`):非空,不含 `/\:*?"<>|`,
  **允许中文**。界面显示用服务定义里的 `label`。
- **它属于语言条目,不属于文件顶层。** 顶层出现 `service` 判**非法** —— 见 §5.5。
- 校验分两级(见 §7):结构校验只看形状,语义校验才查工程内的服务文件是否存在。
- 手工改名服务文件会让引用断链 —— 应用里的"重命名服务"会自动改写引用方(见 §4.7)。

### 5.5 `voices`:每个语言一条,自带全部配置

**必需**,对象,至少一条。键是**精确语言标签**:

- 语言标签与配音资产目录名同源:`assets/<语言标签>/voice_hs/…` 里的那个标签。
  合法形式 `xx` / `xxx`,可带若干 `_region` 段,全小写 —— 即 `isValidLocaleTag` 的判定。
  编辑器写入前先过 `src/i18n/locales.ts` 的 **`formatLocaleTag`**(`zh-CN` / `ZH_CN` → `zh_cn`),
  **不要另写一份归一化**;它认不出的返回空串,直接判非法。
- **只有语言标签这一种键。** 没有 `default` / `*` 这类兜底键,写了即报错(见 §7.1)。
- **不支持语言前缀通配。** `zh` 只匹配标签恰好是 `zh` 的资源目录,**不会**连带
  `zh_cn` / `zh_tw` / `zh_hk` —— 要涵盖多个地区就逐个写。
- **每个条目都是对象,没有字符串简写。**

每个条目把该语言的音色来源**写全**:

| 键 | 必需性 | 说明 |
|---|---|---|
| `service` | **必需** | 服务 id,引用 `meta/voice/service/<id>.ttsservice` |
| `voice` / `clone` | **二选一** | 音色来源,恰好一个,见下 |
| `speed` | 可省 | 语速;不写即 `1.0`(**字段默认值**,不是从别处继承) |

#### 为什么 `service` 在语言条目里,而不是文件顶层

顶层放一个 `service` 当默认、再逐语言覆盖,会让"这个语言到底用哪家"需要**看两处并按优先级推**。
现在没有优先级可推:每条语言自己写全,读到哪条就是哪条。

代价是重复 —— 五个语言就写五遍 `service`。**但重复只发生在文件里,用户从不打开这个文件**
(§前提)。所以这层便利应该长在**编辑器**上,而不是格式里:

- 编辑器提供"改这一条"与 **"应用到所有语言"** 两个动作;
- 格式里则永远只有一种形态,没有"继承来的值"这种要推理的东西。

这与 §前提 第 1 条(一个概念只留一种写法)是同一条:**格式里不给人写便利的糖。**

#### 音色来源:二选一

| 形式 | 写法 | 说明 |
|---|---|---|
| **预置音色** | `{ "voice": "<服务侧音色 id>" }` | 直接给一个 id |
| **克隆** | `{ "clone": { "samples": [...], "consent": "..." } }` | 由样本克隆出 id,应用负责登记与缓存 |

**`voice` 与 `clone` 恰好有一个,同时出现或都没有都判非法。**
一个语言的音色只有一个来源,两者并存会让"到底用哪个"产生歧义,
校验器也给不出确定结论。

> 编辑器切换来源时要**清掉另一侧的字段**。切到预置音色后,原先的样本资源
> 仍留在 `assets/` 里(不自动删 —— 用户可能只是临时对比),但 `.tts` 里不再引用它。

#### `voices` 的键 = 录音棚里可选的语音方案

既然没有兜底项,`voices` 里配了什么,录音棚里就能选什么 —— **不多不少**:

- **没配的语言不出现在语言方案列表里。** 这是"选不到",不是"报错" ——
  也就是说是**能力清单**,不是"必须覆盖所有配音语言"的强制映射。
- 与工程实际的配音语言**不要求一一对应**:先配好音色、后补翻译是正常顺序;
  反过来,有配音但没配音色的语言,就是暂时不打算用 TTS 生成。
- 结构校验判不了这件事(它不知道 `assets/` 里有哪些语言),而语义校验**也不该判** ——
  这里没有错误可言。唯一的效果是录音棚那一级少一个选项。

详见 §7.4。

### 5.6 克隆来源:`voices.<k>.clone`

克隆写在**该语言的音色条目里**,不是与 `voices` 并列的另一块:

```json
"voices": {
  "zh_cn": { "service": "minimax-main", "voice": "linwan_v1" },
  "en_us": {
    "service": "elevenlabs-main",
    "clone": {
      "samples": ["assets/voice-samples/林晚/en_us/01.wav"],
      "consent": "meta/docs/声音授权-林晚-en_us.md"
    }
  }
}
```

`clone` 对象只有两个键:

| 键 | 必需性 | 说明 |
|---|---|---|
| `samples` | **必需** | 数组,≥1 项,每项是 `assets/` 下的资源路径 |
| `consent` | **必需** | 同意凭证的引用 |

**`samples` 不设数量上限。** 真正的限制来自服务商的接口(时长、体积、格式),
超了会被它自己拒掉 —— 规范再卡一个自己的数字,只会让后来的人不知道为什么是这个数。

**没有 `voiceId`。** 克隆出的 id 由应用按
`服务id + 样本内容哈希` 登记在应用侧;`.tts` 里那个人写的 `voice` 用于"我已经有音色了,
直接引用"。两者正是二选一的两条路。

#### 硬规则一:样本是 **assets 资源引用**

`samples` 里的每一项都是 `assets/` 下的资源路径,**由资源系统管理**:

```json
"samples": ["assets/voice-samples/林晚/en_us/01.wav"]
```

**不规定目录。** 只要求是合法的资源路径(即 `normalizeAssetPath` 能通过:
`assets/` 前缀、无 `..`、无 `:`、无连续斜杠)。具体放哪一层由使用者和编辑器决定。

好处是样本和其它资源一样,自动获得整套资源能力:

- 出现在**资源管理器**里,可预览、可拖拽导入、可改名;
- 保存工程时随 assets **整树重写**,不需要单独的读写通道;
- 因为它是工程资产的一部分,**跟着工程走**。

**它不会进 PAK。** `resourcePack` 是**选择性导出**:只认
`assets/<语言标签>/lang_<后缀>/…` 与 `assets/<语言标签>/voice_<后缀>/…` 两种布局
(且只导出被 `.hsc` 引用到的键),其余资产一律跳过。放在别处的参考音频因此出不了厂。

> 这意味着落点由**布局**决定,而不是由"在不在 `assets/` 里"决定。
> 将来若要扩大 PAK 的收录范围,**必须同时排除样本目录**。

#### 硬规则二:`consent` 必需,且是引用

声音是**生物特征数据**。主流厂商全都要求"声音所有者明确书面同意"才允许克隆:

| 厂商 | 同意要求 |
|---|---|
| Azure | Limited Access 申请 + 录制口述授权 + **声纹核验**(比对授权录音与训练音频是否同一人) |
| ElevenLabs | 内建同意机制;专业克隆加 voice captcha 验证 |
| OpenAI 定制声音 | 声优按指定语句录制同意录音,与样本一并提交;每组织上限 20 个 |
| MiniMax | 上传即代表已获授权(ToS 层面) |

GDPR 把声音算生物特征数据;EU AI Act 另要求披露 AI 生成内容。
**规范能做的是:让"没有同意"这件事在编辑期就写不出来。**

```json
{ "consent": "meta/docs/声音授权-林晚-zh_cn.md" }
```

同 §5.3 的思路:凭证本身不进 `.tts`,只放引用。区别是密钥怕泄漏、同意书怕丢失,
所以同意书允许指向工程内的 `.md` —— 它本来就是"创作资料"。编辑器里这一步是
"上传授权书"按钮,落盘时自动归位到 `meta/docs/`(扁平,文件名需唯一)。

#### 硬规则三:能不能克隆,**由服务商决定**

写 `clone` 不等于能克隆。这是**服务的能力**,不是角色方案的属性 ——
所以判断依据是**该语言条目里 `service` 指向的服务定义**,而不是 `.tts` 里写了什么。

能力分两级,取决于协议与账号:

| 预设 `provider` | 协议是否提供克隆 | 默认是否可用 |
|---|---|---|
| `elevenlabs` | ✅ 提供 | ✅ 默认可用 |
| `minimax` | ✅ 提供 | ✅ 默认可用 |
| `azure` | ⚠️ 提供但受限 | ❌ **默认不可用** —— Limited Access,只有微软托管客户可申请 |
| `openai` | ⚠️ 提供但受限 | ❌ **默认不可用** —— 需 sales 审批,每组织 ≤20 个 |
| `google` / `polly` | ❌ 不提供 | ❌ 无法开启 |

**协议不提供的,连接也开不了**(`google` / `polly`);**协议提供但受限的,由连接显式开启**
(Azure 拿到 Limited Access、OpenAI 过了审批之后,在该连接上打开)。

落地就是服务定义上的 `capabilities`,规则见 §4.6:**只能收窄,不能放宽**。

```jsonc
// meta/voice/service/azure-main.ttsservice
{
  "version": 1,
  "label": "Azure 东亚",
  "provider": "azure",
  "auth": { "apiKeyRef": "app:azure-speech" },
  "baseUrl": "https://eastasia.tts.speech.microsoft.com",
  "capabilities": ["clone"]          // 拿到 Limited Access 之后显式打开
}
```

校验行为:

- `voices.<k>.clone` 出现 → 该语言的**服务定义**必须在其 `capabilities` 里含 `clone`,
  否则判非法(错误信息指出是哪个服务、缺哪项能力)。
- **编辑器根本不显示"克隆"这个选项**,当该服务不具备能力时 ——
  用户不该先选了一个做不到的东西,再被报错拦下。

#### 克隆是**一次性登记**

克隆接口是上传样本换一个 `voice_id`,之后合成走普通 TTS 端点。所以:

- 应用侧维护 `服务id + 样本内容哈希 → provider voice_id` 的登记表,存在应用级存储;
- 首次合成时:命中就直接用;没命中就上传样本 → 克隆 → 登记;
- 登记表失配时(换账号、换机器、厂商重置)重新克隆并更新登记表 ——
  **不需要改 `.tts`**,因为 `.tts` 里存的是样本,不是 id。这也是"二选一"结构的一处红利:
  克隆的那条路不暴露 id,就没有"id 失效要回写文件"的问题。

#### 克隆接口形态

| 协议 | 流程 | 限制 |
|---|---|---|
| `elevenlabs` | `POST /v1/voices/add`(multipart 上传样本) | 专业克隆需 captcha 验证 |
| `minimax` | `POST /v1/files/upload`(`purpose=voice_clone`)→ `POST /v1/voice_clone` | 10s–5min、≤20MB、mp3/m4a/wav;`voice_id` 8–266 字符、首字母为英文字母 |
| `azure` | Speech Studio / CNV | 审核 5–10 工作日 |
| `openai-compatible` | `POST /v1/audio/voices` | 需审批,每组织 ≤20 个 |

## 6. 编辑器分层

| 编辑器里的控件 | 落点 | 用户改得了吗 |
|---|---|---|
| 语言行(增删) | `.tts` → `voices` 的键 | ✅ 增删 |
| 服务(下拉,选项来自工程内的 `meta/voice/service/`) | `.tts` → `voices.<k>.service` | ✅ **逐语言**选(末项是"新建服务…") |
| 音色(可试听的列表) | `.tts` → `voices.<k>.voice` | ✅ **逐语言**选 |
| 语速 | `.tts` → `voices.<k>.speed` | ✅ **逐语言**拖 |
| 该语言"用预置音色 / 用克隆"切换 | `.tts` → `voices.<k>` 的 `voice` 或 `clone` | ✅ 单选 |
| 克隆样本、授权书 | `assets/`、`meta/docs/` + `.tts` → `voices.<k>.clone` | ✅ 上传 |
| **"应用到所有语言"** | — | ✅ 一键把当前条的服务/音色/语速刷到每条(§5.5 的补偿机制) |
| **"克隆"这个选项本身** | — | ⛔ **该语言**的服务不具备能力时**不显示** |
| 服务的显示名 | `meta/voice/service/<id>.ttsservice` → `label` | ✅ 改 |
| 选 `provider`(含"新建预设…"/"用 `template` 临时连接") | `meta/voice/service/<id>.ttsservice` → `provider` | ✅ 选 |
| 协议、端点、模型、凭据引用、能力开关 | `meta/voice/service/<id>.ttsservice`(**另开服务编辑器**) | ⛔ 不在角色编辑器里 |
| 预设的增删改(自建那批;内置只读) | **应用级存储**,不进工程 | ✅ 可增删 |
| **密钥本身** | 本机凭据库 | ✅ 只在凭据库填,**不落工程** |
| **②语言方案列表**(录音棚) | **只列 `voices` 里的键**;没配的不出现 | ⛔ 由配置决定 |
| **①角色方案列表**(录音棚) | 只列 `meta/voice/` 下的 `.tts`;没有的不出现 | ⛔ 由文件决定 |
| 输出格式(wav / pcm / mp3) | **不落盘** | ⛔ 适配器按协议取无损档 |
| 文本切分、单请求字符上限 | **不落盘** | ⛔ 适配器按协议已知上限 |
| 语言码翻译(`zh_cn` → `zh` / `zh-CN`) | **不落盘** | ⛔ 适配器读 `src/i18n/locales.ts` |
| 单声道 Vorbis `.ogg` | **不落盘** | ⛔ 规范强制,走 `runVoiceImport` |
| 角色名 | 文件名 | ⛔ 改名即改键 |

**"不落盘"那一档是关键。** 它们不是"编辑器里隐藏了",而是**文件里根本不存在** ——
所以导出工程、贴到 issue、被 Agent 读到时,都没有多余的细节可泄漏。

## 7. 校验规则

### 7.1 结构校验(只看 `.tts`,离线可跑)

| 路径 | 规则 |
|---|---|
| 文件名 | 去 `.tts` 即角色名;非空,不含 `/\:*?"<>\|` |
| `version` | 必需,必须为 `1` |
| `character` / `name` / `id` | **不允许出现**(角色名只来自文件名) |
| `service` / `speed` | **不允许出现在顶层**(它们属于语言条目,见 §5.5) |
| `voices` | 必需,对象,键数量 ≥ 1 |
| `voices.<k>` | 键**必须**是合法语言标签(`isValidLocaleTag`)—— 没有 `default` 之类兜底键;值必须是对象 |
| `voices.<k>.service` | **必需**,非空字符串(它能解析到哪个服务文件属 §7.2 的语义校验) |
| `voices.<k>` 的音色来源 | **`voice` 与 `clone` 恰好有一个** —— 都有或都无判非法 |
| `voices.<k>.voice` | 给了 `voice` 时必需,非空字符串 |
| `voices.<k>.clone` | 给了 `clone` 时必需,对象 |
| `voices.<k>.clone.samples` | 必需,数组、≥1 项、每项非空字符串 |
| `voices.<k>.clone.samples[*]` | 必须是合法资源路径 —— **直接走 `normalizeAssetPath`**(`assets/` 前缀、无 `..` / `:` / 连续斜杠),返回 `null` 即判非法 |
| `voices.<k>.clone.consent` | 必需;`meta/` 下路径,或匹配 `^(env\|app):[A-Za-z0-9_.-]+$` |
| `voices.<k>.speed` | 可省,数值 |
| 未知键 | **警告**,不报错(见 §9 的保留规则) |

> 顶层的 `service` / `speed` 判**错误**,不按"未知键"放过 —— 它们是**认识的键放错了位置**。
> 当警告放过的话,用户会以为顶层那个值生效了,而实际读的是语言条目里的值。
> 这与 §5.1 拒绝顶层 `character` / `name` 是同一条思路:**歧义输入要在结构校验就拦掉。**

### 7.2 语义校验(需要工程内的服务定义 + 本机凭据状态)

| 检查 | 说明 |
|---|---|
| **服务文件存在** | 每个 `voices.<k>.service` 都要能在 `meta/voice/service/` 里找到同名 `.ttsservice`,否则报错 |
| **克隆能力** | `voices.<k>.clone` 出现时,该语言的**服务定义**必须在其 `capabilities` 里含 `clone`,否则报错并指出是哪个服务 |
| `voice` 可用 | 音色 id 能在该服务下解析(预置音色枚举) |
| **凭据已配置** | 该服务的每个 `*Ref` 在本机都能解析(env / 凭据库)。缺失时**只提示不报错** —— 协作者打开工程时必然缺凭据,那不是文件的问题 |
| 语速区间 | 各协议不同(OpenAI `0.25–4.0`、MiniMax `0.5–2.0`、ElevenLabs `0.7–1.2`),越界时**警告**并钳制,不报错 |
| 样本资源存在 | `voices.<k>.clone.samples` 指向的路径在 `pkg.assets` 里能找到对应的资源 |

编辑器在写入前跑两级校验,所以用户基本看不到校验失败。结构校验器仍要独立可跑
(`scripts/verify-tts-spec.ts`),用途是:Agent 写文件后的兜底、旧工程加载时的兼容检查、
以及排查用户贴出来的文件。

### 7.3 服务定义文件的校验(不依赖 `.tts`)

每个 `meta/voice/service/*.ttsservice` 有自己的完整规则,可独立校验:

| 路径 | 规则 |
|---|---|
| 文件名 | 去 `.ttsservice` 即 id;合法资源名;`meta/voice/service/` 内**唯一** |
| `version` | 必需,必须为 `1` |
| `id` | **不允许出现**(id 只来自文件名,同 §5.1 的理由) |
| `label` | 可省,非空字符串 |
| `provider` | 必需,∈ §4.3 预设表(内置 ∪ 用户自建) ∪ `{"template"}` |
| `protocol` | **预设时**可省,写了必须等于预设的协议;**`template` 时必填**,∈ §5.2 枚举 |
| `auth` | 必需,对象;其中每个 `*Ref` 键匹配 `^(env\|app):[A-Za-z0-9_.-]+$` |
| `auth` 形态 | 必须匹配该协议要求的凭据形态(单值 / 双值 / service account) |
| `baseUrl` | 预设时可省、可覆盖;**`template` 时必填**;必须 `https://`(允许 `http://localhost`) |
| `model` | 可省。预设时若填,应在预设的模型候选里(**警告**,不报错 —— 厂商上新快于应用发版) |
| `capabilities` | 可省。**必须 ⊆ 预设「协议提供的能力」**;超出判非法 |
| 未知键 | **警告**,不报错(见 §9 的保留规则) |

**`capabilities ⊆ 预设` 是硬规则**,不是警告 —— 它是"克隆由服务商约束"的执行点。
放宽能力等于让用户声明一个服务商没提供的能力,后面必然运行时失败。

### 7.4 未配置的角色 / 语言:选不到,而不是报错

`.tts` 只在录音棚里被使用,而生成配音是**两级选择**:

```
① 选角色配音方案（meta/voice/*.tts）
        ↓  没有 .tts 的说话人不出现在这一级
② 选语言方案（该 .tts 的 voices 键）
        ↓  该 .tts 里没配的语言不出现在这一级
   开始生成
```

- **两级都必须选。** 缺任一级就不能生成 —— 按钮不可用,**不弹错误提示**
  (还没开始做的事不算错)。
- 第①级没有可选项 = 工程里一个 `.tts` 都没有,先建方案。
- 第②级没有可选项 = 这份 `.tts` 的 `voices` 是空的 —— 但它建不出来(§7.1 要求 ≥1 条)。
- **不设"应用级默认音色"。** 没有方案的角色就是不能生成 TTS —— 想要就给它建一份 `.tts`。
  这是"没有兜底"的直接后果:兜底会让同一个角色在不同工程里发出不一样的声音,
  而且会让"为什么这个角色有声音"变得没法从文件回答。

> 注意区分:**"没配"不是错误,是没这个能力。** 既然第②级只有 `voices` 里那几个选项,
> 就不存在"选了一个没配的语言"这种状态 —— 状态从入口就排除了。

## 8. 磁盘布局

```
<工程>/
├── project.json
├── <剧本名>.lang.<语言标签>     语言文本（名字由 `.hs` 派生，留在包根）
├── src/
│   ├── hanshu/     *.hs        剧本（源）
│   ├── character/  *.char      角色卡（源）
│   └── scripts/    *.py        脚本（源）
├── meta/                       创作资料 —— 不进 PAK
│   ├── docs/       *.md        说明文档、声音授权书（**扁平**）
│   └── voice/                  TTS 配音配置
│       ├── *.tts               角色配音方案（扁平，文件名 = 角色名）
│       └── service/
│           └── *.ttsservice    TTS 服务定义（扁平，文件名 = 服务 id）
└── assets/                     资源 —— 由资源系统管理
    ├── <语言标签>/
    │   ├── lang_<后缀>/…       ← 这两种布局会进 PAK（选择性导出）
    │   └── voice_<后缀>/…  *.ogg
    └── voice-samples/…  *.wav  ← 克隆参考音频（可直接被 .tts 引用）
```

### 为什么服务定义放在 `meta/voice/` 底下

- **它只服务于 TTS。** 放进 `meta/service/` 这种通用名字,会让后来者以为它是某种全局服务注册表,
  将来别的东西也往里塞。挂在 `meta/voice/` 下则天然说明:**这是配音这一摊的子配置。**
- **配置跟着它的使用者走。** 角色方案和服务定义是同一条链上的两级 ——
  一个说"这个角色用什么声音",一个说"这个声音从哪个账号出"。放在同一棵子树里,
  删掉整个配音功能就是删掉一个目录。
- **后缀 `.ttsservice` 自证用途。** 仓库是按后缀归位的,而 `getExtension` 取的是
  **最后一个点之后的全串**(`/(\.[a-z0-9]+)$/`),所以 `x.ttsservice` 必定解析成 `.ttsservice`,
  不会掉到 `.tts` 上 —— 两类文件一眼能分辨,不会把服务定义当成角色方案。

**`meta/` 下只有 `docs/` 与 `voice/` 两个目录。** `meta/schema/` 不存在 —— 它曾经是
`.tts` 的落点,`.tts` 搬到 `meta/voice/` 之后就只剩一个空占位,已删掉。
本项目没有"需要落盘的 schema 文件":校验器的元数据是**代码里的数据**(见 §4.3 的预设表),
不是工程里的文件。

`meta/voice/` 与 `meta/voice/service/` 装的是**实例**(每个角色一份方案、每个账号一份服务定义)。
两处文件都**扁平**:文件名即键,不允许再往下分目录。

`voice-samples/` 只是本文档为示例取的目录名,不是规定 —— 样本放 `assets/` 下哪一层都行。

## 9. 版本与迁移

应用是文件主,版本策略必须明确。

**`.tts` 与 `.ttsservice` 各自带 `version`,各自独立迁移** —— 服务定义升版不该逼着角色方案一起升版。
下面这套规则对两类文件同样适用。

| 情况 | 行为 |
|---|---|
| `version` 等于当前版本 | 直接用 |
| **更低**版本 | **内存里迁移**到当前版本;不立刻落盘,下次保存时写新版本 |
| **更高**版本 | **拒绝打开该文件**并提示升级应用。**绝不静默降级** —— 新版本可能已改字段语义,降级写入等于损坏数据 |
| **未知键** | **原样保留**,回写时带上,不删。跨版本往返不丢数据 |
| 迁移失败 | 报告具体键与原因,原文保留不覆盖 |

读写分离:**读要宽容**(老版本、未知键都能进),**写要严格**(只写当前版本的规范形状,
外加保留下来的未知键)。这与 `.lang` / `.voice` 上已有的保真写入思路一致,
可直接复用 `appendJsonObjectEntries` 的经验。

## 10. 落地影响

### 10.1 目录与映射改动

- `src/workspace.ts`:`FILE_DIRS` 改一项、增一项 —— `'.tts'` → `'meta/voice'`,
  新增 `'.ttsservice'` → `'meta/voice/service'`;`ALLOWED_EXTENSIONS` 加上 `.ttsservice`;
  `editorLanguageForFile` 给 `.ttsservice` 也返回 `'json'`;`.ttsservice` 加进
  `MANUAL_FILE_EXTENSIONS` 的黑名单(服务只经服务编辑器创建,不允许手建一个没有 `provider` 的文件)。
  同时改掉 `FILE_DIRS` 上方那段注释(`meta/schema` 已不复存在)。
- **`meta/voice/service/` 这种两层目录不需要改 `projectFs.ts`。** 归位校验比较的是
  `${dirName}/${path}` 与 `sourceRelativePath(name)`,`writeFileAtPath` 会沿途建中间目录,
  `listFilesRecursive` 本来就递归 —— 两处都已经支持任意深度。
- `src/agent/rules.ts`、`src/agent/tools.ts`:工程结构描述同步(含 `list_sources` 的说明)。
- **工具工作区必须经 `ScriptWorkspace` 的包内文件通道读写,不能直接写盘。**
  工程的内存包才是真相,而保存时会清掉"不在包里的文本文件" —— 绕过它写盘的文件
  在下次保存时会被当多余删掉;如果那个文件正在资源编辑器里打开,还会被旧正文覆盖回去。
  所以 `ScriptWorkspaceHandle` 加了 `listPackageFiles` / `readPackageText` / `writePackageText`
  三个方法,`TtsServiceWorkspace` 是第一个使用者。
- **`meta/schema/` 已删。** 因为 `.tts` 从未有过更高版本,不存在"旧工程需要迁移"的情况;
  磁盘上若残留一个空的 `meta/schema/`,它不属于 `FILE_DIRS` 的任何归位目录,
  保存时的清理逻辑不会碰它 —— 由用户自行删除即可,不必写迁移代码。
- **新增文件类型 `.ttsservice` 的代价已经算过**:一条 `FILE_DIRS` 数据 + 一个编辑器面板。
  不需要新的读写通道 —— `meta/` 下的文本文件本来就走同一套保存/加载机制。

**协议实现进度**:

| 协议 | 状态 | 备注 |
|---|---|---|

**克隆的上传**(§5.6):

| 协议 | 状态 | 流程 |
|---|---|---|
| `elevenlabs` | ✅ | `POST /v1/voices/add`,multipart(`name` + 重复的 `files`)→ 回 `voice_id` |
| `minimax` | ✅ | `POST /v1/files/upload`(`purpose=voice_clone`)→ `file_id`;再 `POST /v1/voice_clone` |
| `azure` / `openai-compatible` | ⛔ | 需人工审批,拿到后到厂商控制台建音色 |
| `google` / `polly` | ⛔ | 协议不提供克隆 |

两处实现细节值得记下,免得后来者以为写错了:

- **MiniMax 的 `voice_id` 是客户端提供的**,响应里不回传 —— 它只回 `base_resp`。
  格式还有硬约束:≥8 字符、字母开头、**必须含数字**。所以从样本指纹派生
  (`hs1` + 指纹),好处是**可复现**:同一批样本重新克隆得到同一个 id,不会在厂商侧堆重复音色。
- **MiniMax 的国际端点不带 `GroupId`**,国内端点(`api.minimaxi.chat`)才要。
  预设用的是国际端点,所以不做那条分支。

|---|---|---|
| 服务编辑器 | **工作区** —— 等效直接编辑 `meta/voice/service/*.ttsservice` | `workspaces/TtsServiceWorkspace.tsx` |
| 配音方案编辑器 | **工作区** —— 等效直接编辑 `meta/voice/<角色>.tts` | `workspaces/TtsPlanWorkspace.tsx` |

工具工作区**不能直接写盘**:保存工程时会清掉"不在内存包里的文本文件",绕过它写盘的内容

- **无损音频档** —— 见 §11.2。

### 10.3 服务编辑器与凭据库(两块新 UI)

服务定义是**工程文件**、凭据是**本机数据** —— 所以是两块,不是一个页面。

1. **服务编辑器**(读写 `meta/voice/service/*.ttsservice`)
   - 新建时输入名字 → 它既是文件名(id)也是默认 `label`;`label` 之后可单独改。
   - 选 `provider` → 带出默认协议 / 端点 / 模型 → 可覆盖端点 / 模型 → 可收窄能力。
     表单按预设的凭据形态渲染(单值 / 双值 / service account)。
   - 供应商下拉的末两项是**"新建预设…"**与**"用 `template` 临时连接"**(见 §4.3 / §4.4)。
   - **重命名服务时自动改写所有引用它的 `.tts`**(见 §4.7)。
   - 角色编辑器里的服务下拉末项是"新建服务…",不必先离开角色再回来。
2. **预设管理**(一个可增删的列表,不是只读表格)—— 见 §4.3「插件式」。
   - 内置那一批住在 `src/tts/providers.ts`,是代码里的数据,随发版增补,**只读**;
   - 用户自建那一批住应用级存储,不跟版本走,与内置**同权**,只要求**不与内置重名**。
3. **凭据库**(应用级)—— 存真实的密钥,按 `*Ref` 里的名字索引。
   沿用 `localStorage` + `hanshu.*` 键命名。
4. **"测试连接"按钮** —— 用当前配置发一次极短合成,把错误直接暴露在服务编辑器里。
5. **开工前的凭据体检** —— 打开工程时比对"这个工程用到哪些 `*Ref` / 本机缺哪几个",
   列成一张待填清单。**这是协作场景下唯一必须重做的一步**(见 §7.2)。
6. **录音棚的两级门禁** —— 生成配音前必须选定 `.tts` 与语言方案;
   两级下拉的内容完全由配置决定,**缺的项不出现、不报错**(见 §7.4)。

### 10.4 其他

- 编辑器高亮:`editorLanguageForFile` 已把 `.tts` 映射为 `'json'`,给 `.ttsservice` 补一行即可。
  **`monaco-yaml` 不需要** —— 两类文件都是 JSON,校验靠代码里的校验器,
  不靠 schema 文件。这也是 `meta/schema/` 被删掉的原因之一(见 §8)。
- `src/assets/paths.ts` 的 `isJsonAsset` 不含 `.tts` / `.ttsservice`,不受影响。若将来要在资源树里
  预览它们,需把它们归入文本资产。
- **克隆样本走 `normalizeAssetPath` 校验**,不要另写一套路径检查。它的规则
  (`assets/` 前缀、无 `..` / `:` / 连续斜杠)正好是样本需要的。
- `resourcePack` 目前靠"布局不匹配就跳过"来排除样本。这条依赖是**隐式的** ——
  若将来扩大 PAK 的收录范围,要显式排除样本目录(见 §5.6)。

## 11. 已定与未决

### 11.1 已定的(留档,避免反复讨论)

| 问题 | 结论 | 落在 |
|---|---|---|
| 克隆样本数量上限 | **不设上限**,由服务商接口约束 | §5.6 |

### 11.2 仍未决

1. **凭据的落盘方式**:服务定义已定落 `meta/voice/service/*.ttsservice`(跟工程)。
   `*Ref` 指向的**真实密钥**落哪?`localStorage` 还是 Tauri 安全存储?
   若走 Tauri 命令代发请求(可彻底避免前端暴露密钥,也绕开 CORS),
   则请求/响应 DTO 要另立 `src/tts/contracts/`。
2. **音色列表缓存**:各家的 `voices/list` 形态不一(Azure / Polly 有,OpenAI 是固定枚举,
   ElevenLabs 有 `/v1/voices`,MiniMax 的克隆音色要单独查)。预设档里已经要写"音色来源",
   具体形态待定。
3. **用户自建预设的导入导出**:预设住应用级存储,不跟工程走。那换机器时要不要能导出?
   若要,它是"设置备份"的一部分,里面的 `*Ref` 同样只能放引用(见 §5.3)。
4. **`.tts` 的保真写入**:未知键要原样保留(§9),这要求编辑器读写时不做"整体重建"。
   `.lang` / `.voice` 已有 `appendJsonObjectEntries` 的经验可复用,具体落法待定。
5. **无损音频档**:OpenAI 的 `response_format: "wav"` 与 Azure 的
   `riff-24khz-16bit-mono-pcm` 有文档依据,已直接用。但 ElevenLabs 只有 MP3 与
   **无头裸 PCM**(要自己包 WAV 头,且需 Pro 档),MiniMax 的 `format` 枚举只见到 `mp3`
   的样例 —— 这两处现在走 MP3,**多一次有损**。要全无损得做一层裸流包 WAV 头,
   并且要真实账号确认档位。
6. **`requires_verification`**:ElevenLabs 建完音色会回一个 `requires_verification`
   —— 为真时音色可能还不能用。现在拿到 id 就登记,没管这个标记。
   要不要在它为真时提示"等厂商审核"?
7. **MiniMax 的克隆保活**:文档说克隆出的音色**7 天内至少用一次**,否则会被自动删除。
   要不要在登记表里记一个最近使用时间,超期前提醒?现在没做。
