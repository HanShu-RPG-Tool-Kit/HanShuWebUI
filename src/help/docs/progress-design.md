# 进度：任务与委托（策划草案）

> 状态：**草案**。对齐引擎侧的进度系统与 WebUI 表单；尚未实现编辑器。  
> 进度 ≈ 委托 / 挑战条目。**不要**礼包式继承与组合。  
> 进度与**故事流程**平级；流程去引用进度**可以，但不推荐**。

---

## 0. 在引擎里的位置

```text
进度流程系统
├─ 数据状态
│   ├─ 对象统计计数器（player → key → 整数 / 浮点 / 时间）
│   ├─ 对象进度记录表（player → table → tuple）
│   └─ 对象变量表（player → mapping → key → value）
├─ 条件与表达式求值器（AviatorScript）
├─ 目标管理器（Goal：由内置 / 项目内 py 注册）
├─ 进度系统（委托 / 挑战）     ← 本文
├─ 流程系统（主线 / 支线故事） ← 与进度平级
└─ （成就系统：砍掉，暂不做）

+ Redis 等基础设施
```

| 子系统 | 管什么 |
| --- | --- |
| **目标** | 「这件事满足了吗」；**种类**用 py 扩展（事件、计数等） |
| **进度** | 接取 → 进行 → 交付 / 失败 / 放弃；**大量同构**的委托条目 |
| **流程** | 故事阶段怎么走（`.hflow`） |

进度批量、形状像；目标与流程才是「花样」更多的地方。进度不要再平行搞一套 gate/logic 脚本注册表——特例交给**条件求值器**。

## 1. 进度实例状态机（引擎已定）

```text
未接受
  │  可接受且玩家接受
  ▼
进行中 ──（处理中 / 可交付）
  │
  ├─ 可交付且交付 ──► 已结束（完成）
  ├─ 失败 ──────────► 已结束（失败）
  └─ 可放弃且放弃 ──► 已结束（放弃）

已结束（·）── 再次可接受且接受 ──► 进行中
```

表单描述规则；实例在进度记录表里由进度系统推进。

## 2. 产品立场：同构表单 + 默认规则 + 表达式特例

### 2.1 为什么不强拓展进度本身

委托 / 日常 / 挑战在作者眼里大多是同一张表：挂几个目标、设门槛、设刷新、挂礼包。  
**可拓展性应主要花在 Goal 种类上**（新事件、新计数方式）；进度侧保持同构，WebUI 好做、好校验、好批量改。

「每张进度一份逻辑 py」或「进度专用脚本种类表」——对这种内容偏重。简单不一定不好。

### 2.2 推荐形态

```text
进度表单（几乎每张都一样）
  ├─ 展示与标签
  ├─ 目标列表 + 目标组（all / choose_n / any / optional）
  ├─ 可接取条件：默认规则 和 / 或 条件表达式
  ├─ 可交付 / 完成 / 失败：默认规则 和 / 或 条件表达式
  ├─ 重复与冷却（枚举）
  └─ 奖励（引用 .kit）

脚本
  └─ 目标定义/     ← 继续用 py 扩展「做什么」
     （不必为进度再开 进度条件/、进度逻辑/ 目录）
```

| 需求 | 做法 |
| --- | --- |
| 常见接取 / 完成 | **引擎默认**：例如「非 optional 组均满足 → 可交付」；冷却策略自动并进可接取 |
| 特例门槛 | 作者写 **Aviator 条件表达式**（可接取、可交付、失败等槽位） |
| 新玩法动作 | 新 **Goal 种类**（py），进度仍只是挂目标 |

默认与表达式的关系建议：

- 某槽位**留空** → 走默认。  
- **填写表达式** → 以表达式为准（或与默认 AND，首版建议「填写即覆盖」，规则更少歧义）。  
- 表单可提供「插入常用片段」（等级、标记、某 goal 已满足），仍是表达式，不是第二套种类系统。

### 2.3 和故事流程的边界

- 流程：故事图。进度：委托生命周期。平级。  
- 协作优先共享数据状态 / 目标满足态；不鼓励流程节点直接接取、交付进度。

## 3. 表单块（作者侧）

### 3.1 身份与展示

稳定 ID、名称、简介、`tags`。无继承组合。

### 3.2 目标挂载与目标组

每一行 = 目标定义目录里的 `@goal` kind + 由其 `@config` 展开的字段。种类**不**写死在进度表单里，唯一来源是「脚本 → 目标定义」下的 py（`buildGoalDefinitionCatalog`）。  
组种类仍用数据描述完成结构（由引擎默认完成逻辑解释）：

| 组 | 含义 |
| --- | --- |
| `all` | 必修 |
| `choose_n` | 选择性必修 |
| `any` | 多种完成方式 |
| `optional` | 选修，不挡可交付 |

### 3.3 条件槽（默认 + 表达式）

| 槽位 | 默认（示意） | 表达式特例 |
| --- | --- | --- |
| 可接取 | 冷却已结束；可选「无进行中的同一进度」等 | `level >= 10 && dialogue.after('…')` |
| 可见（可选，可与可接取合并） | 同可接取或更宽 | 同上 |
| 可交付 | 目标组默认语义已满足 | 额外要求交物品、在区域内等 |
| 失败（可选） | 无自动失败 / 仅超时策略 | `hp <= 0` 或标记类 |
| 可放弃 | 常量 true/false | 很少需要表达式 |

表达式求值上下文应稳定暴露：玩家计数器 / 变量、进度记录、已挂目标的满足态、冷却状态等（具体 API 由引擎定）。作者写特例时靠文档与「插入片段」，不靠再学一套 py 装饰器。

### 3.4 重复与冷却

`once` / `game_daily` / `game_weekly` / `real_daily` / `real_weekly` / `real_monthly` / `duration` / `manual`。  
写入记录表；**默认可接取**已包含「冷却完毕」。特例要「冷却未完但 VIP 可接」→ 可接取表达式里显式写。

### 3.5 奖励

引用 `.kit`。

## 4. 条件求值器扮演什么角色

Aviator（或引擎统一的条件求值器）是进度侧的**正规特例通道**，不是临时补丁：

- 与数据状态、进度记录、goal 满足态只读对接。  
- WebUI：多行 / 单行表达式编辑 + 校验 + 常用插入。  
- 不替代 Goal：要订事件、累加计数，仍做 Goal；表达式只问「现在真不真」。

与「进度专用 py 闸门 / 逻辑种类」相比：同构内容更少概念、更少生成物、特例又够用。若将来表达式里反复出现同一长模式，再考虑**引擎加默认**或**表达式函数 / 片段库**，而不是先上脚本注册表。

## 5. 可拓展性档位（修订）

| 层级 | 档位 |
| --- | --- |
| 进度实例 | **数据驱动、同构**；弱种类扩展 |
| 接取 / 完成特例 | **条件表达式** |
| 玩法单元 | **Goal py 种类**（强扩展放这里） |
| 改状态机本身 | 改引擎 |

不为作者默认提供「本进度逻辑 py」。比较简单是有意的。

---

## 6. 刻意不做（首版）

- 进度继承 / 组合、成就  
- 进度专用 gate/logic 脚本目录与装饰器体系  
- 用 `.hflow` 画进度，或鼓励流程驱动接取 / 交付  
- 开放嵌套布尔树编辑器（组种类 + 表达式槽足够）  
- 进度内联整份礼包  

---

## 7. 编辑器预想

1. 名称、简介、标签  
2. 目标列表与目标组  
3. 条件区：各槽位「默认 / 自定义表达式」切换  
4. 重复与冷却  
5. 奖励礼包  
6. 摘要：人话复述默认 + 已填表达式  

---

## 8. 开放问题

1. 表达式覆盖默认，还是与默认 AND？（草案偏覆盖。）  
2. 可交付后是自动结算还是玩家交付动作触发。  
3. 表达式上下文的正式符号表（goal 满足态如何引用）。  
4. `choose_n` 未选项是否仍订阅事件。  
5. 进度文件格式（一份 JSON 即可的话最省事）。

---

## 9. 小结

- 进度 ∥ 流程；大量**同构**委托，不追求进度本体的强脚本扩展。  
- **默认规则**覆盖常见可接取 / 可交付；**特例写条件表达式**。  
- 真正要扩展的是 **Goal 种类（py）**；进度表单只挂载与组合。  
- 不做进度专用逻辑脚本体系；不做继承组合与成就。
