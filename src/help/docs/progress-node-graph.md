# 多进度节点图：节点、端口与信号

本文只描述**画布上实际存在的东西**：有哪些节点、节点有哪些端口、哪些线合法、信号怎么走、模拟器怎么跑。模型语义见 [多进度任务模型](#progress-flow-model)；画布交互规范见 [通用节点编辑器接入规范](#node-editor)。

## 1. 图与文档的对应

`.quest` 的 `format` 为 `hanshu.progress-tree`、`version` 为 1。

界面与文档统一使用「逻辑」「并且 / 或者」「条件」。这是概念名称简化，不改变信号语义、节点身份或文件结构：逻辑节点仍保存在 `transitions`，条件节点仍保存在 `predicates`，两种逻辑输入仍为 `input` / `input2`；已有文档无需迁移。

| 文档部分 | 内容 |
|---|---|
| 开始 | `start`：唯一的「开始进度节点」ID，必须存在于 `progress`。任务标题放在该节点的 `questTitle` 上 |
| 节点集合 | `progress`、`predicates`、`objectives`、`transitions`、`ends` |
| 连线 | `logic.links: { id, from, to, port, fromPort? }[]`；`port` 是目标输入口，`fromPort` 是来源输出口 |
| 布局 | `layout.positions` / `layout.notes` / `layout.groups`，只影响画布 |

- 节点 ID 在整张图内唯一（跨集合也不能重名）。
- **唯一连接约束**：只能从右端口连到左端口，且**不能成环（含自环）**。连接时直接拒绝；文档里手写出环是校验 error。
- **内容**：只有开始进度节点有 `questTitle` / `description`；所有进度节点有 `identifier` / `runningLog`（进行时日志）/ `completedLog`（完成时日志）/ `goals` / `completion`；结束节点有 `title` / `rewardKits`；条件只有 `conditions`，没有标题。进度标识符是非本地化字符串；任务标题、说明、日志与结局标题仍是可本地化的 `FlowText`。

## 2. 节点族总表

|---|---|---|---|---|---|

| `progress`（普通） | 进度 | 216×118 | `input` | `output`、`output2` | 同上 |
| `predicates` | 条件 | 200×84 | 无 | `output` | 真 / 假（模拟器切换） |
| `objectives` | 目标 | 216×118 | 无 | `output`（成功）、`output2`（失败） | 未激活 / 运行中 / 已成功 / 已失败 |
| `transitions` | 逻辑 | 180×96 | `input`（并且）、`input2`（或者） | `output`（通过） | 一轮查询的临时簿记 |
| `ends` | 结束 | 168×112 | `input`（成功入）、`input2`（失败入） | 无 | 已到达（成功 / 失败） |

**端口颜色**：成功口绿、失败口红、激活口蓝；逻辑并且口金、或者口蓝；条件紫；结束成功入绿、失败入红。

### 2.1 开始进度节点

- 任务里**有且只有一个**，由根上的 `start` 指定；不可删除。
- **没有左端口**，所以任何线都连不进去；不能靠 A 激活。
- 任务开始时（模拟器「触发开始」）**直接进入运行中**。
- 有两个右端口（成功 / 失败），和普通进度一样可以结算；结算后沿对应端口发 A。
- 额外内容：`questTitle`（任务标题）与 `description`（任务说明）。

### 2.2 进度节点

- 一个左端口 `input`（多线），两个右端口 `output` 成功 / `output2` 失败（各多线）。
- 内容：`identifier`（进度标识符）、`runningLog`（运行中显示的任务日志）、`completedLog`（结算时显示的日志）、`goals`、`completion`（`all` / `any` / `custom`，自定义时带 `completionGraph`）。
- 标识符在同一 quest 内唯一（包括开始进度与草稿节点），区分大小写；必须非空、无首尾空白、不含换行或制表符，最多 200 字符。不进入 `.lang`，也不随语言切换。内部节点 ID 与标识符分离，改标识符不影响连线。重复或非法值是校验 error，编辑时显示即时提示，模拟与导出前必须修正。
- 收 **A**（`input`）：未激活 → 运行中，**同时向左端口发 C**（激活即消费输入：上游不必再为它等待或重复触发）。其它状态下的 A 忽略。
- 结算（模拟器手动）：运行中 → 已成功 / 已失败，并从对应端口发 **A**。
- 收 **Q**：已成功且 Q 到成功口 → 回 **A**；已失败且 Q 到失败口 → 回 **A**；其余回 **N**。
- 收 **C**：运行中 → 已取消（不转发）；未激活 → 从左端口向上游转发 **C**（自身仍为未激活，之后仍可被激活）；已成功 / 已失败 / 已取消 → 忽略。
- 成功口、失败口都可以没有出连线，这是合法的分支末端；结算时没有下游可广播。它不会直接触发任务结局，但仍遵守激活时消费上游的 C 规则，不能据此保证对其他分支完全没有间接影响。若只剩这种无法通向结束节点的运行中进度，按 §9.4 自动失败。

### 2.3 条件节点

- 没有左端口，一个右端口（多线）。生命周期为 **未激活 → 运行中 → 已关闭**；生效节点随 Quest 启动，草稿保持未激活。
- 内容：`conditions` 与可选的非本地化 `identifier`，没有标题字段（判断规则与单进度任务同一套，组内取「与」）。标识符为空或缺省代表匿名；非空时与进度、目标共享 Quest 内唯一命名空间。匿名节点显示规则摘要。
- **空条件恒假**：不会成立。
- **A 是边沿**：仅运行中假 → 真时向下游广播一次 A；一直为真不重复；真 → 假不发信号。
- **Q 是电平**：仅运行中按**当前**真值回答 A / N；未激活、已关闭均回 N。
- 收 **C**：关闭整个节点，不是关闭某条连线；停止监听和广播，后续 Q 均回 N。不转发 C，不因真值改变或 A 重新打开。
- **实例初始化时整体播报一次**：见 §8。之后只按上升沿增量广播。

### 2.3.1 目标节点（Quest 级后台 goal）

- 一个节点只持有一个 `goal: { kind, params }`，复用进度内 goal 的类型定义与参数控件；必须填写非本地化 `identifier`，不允许匿名，与进度和具名条件共享 Quest 内唯一命名空间。节点级 `submission` 提交方式仍可选。不含进度日志、目标列表或完成组合规则。集合名为 `objectives`。
- 新建目标自动生成不冲突的 `objective_1` 等标识符。旧文档缺少标识符时保留为空供作者补填，不静默替作者命名；空值、纯空白、重复标识符会报错并阻止模拟和导出，草稿目标也适用。
- 没有左端口；成功、失败两个右端口各可多线，分别保存 `fromPort: output / output2`。
- 五态：未激活 →（Quest 启动）运行中 →（实例报告）已成功或已失败；收到 C 进入已关闭。成功、失败是生命周期终态，不是仍运行的结果锁存。生效目标、条件与开始进度同一步初始化；草稿不监听、不结算。
- goal 执行、累计值与完成判定由游戏实例负责；不进入任务 UI 跟踪。图模拟器不执行 goal、不提供累计值面板，只用手动成功/失败结算模拟实例发信号。
- 实例结算先锁存结果，再从对应右端口广播一次 A；已结算后不重复结算。收到 Q 时，已成功且查询成功口，或已失败且查询失败口，回 A；其余回 N。
- 任一状态收到 C 均关闭整个目标，包括已成功、已失败；关闭后两个口的 Q 都回 N，不能再次结算或提交，不转发 C。A 不能激活目标，N 不接收。
- **不维持任务存活**：即使目标运行中且有通向结束的连线，也不改变 §9.4 只检查运行中进度的自动失败规则。不会等待其未来完成。
- Quest 终局后停止监听，拒绝后续结算和广播；保留终局前的生命周期快照。重置恢复未激活。所有运行态均不写 `.quest`。

#### 进度与目标的统一提交格式

- goal 类以 `requires_delivery = True` 显式声明需要交付；未声明默认 False。实现 `deliver` 却未声明 True 是配置错误，不能静默忽略。声明属于脚本运行契约，不放入仅供展示的文件头 JSON。详见[脚本资源](#script-resources)。
- `submission` 缺省代表无需提交；存在则要求手动提交，即使 goal 不需要交付，也可主动配置人工确认。是否配置提交不改变目标必须具名的要求，运行时连线仍按稳定内部节点 ID 定位。
- 提交只有两个字段：`submit_type` 和由该类型决定的 `param`。放在 `progress.<节点ID>.submission`（含开始进度）或 `objectives.<节点ID>.submission`，两者格式、校验一致，不是根级 Quest 属性。

  | `submit_type` | `param` | 含义 |
  | --- | --- | --- |
  | `ui` | 必须为 `null` | 由任务 UI 提供入口，无参数 |
  | `dialogue_injection` | 非空注入点名字符串，不带 `@` | 使用对话注入点提供提交入口 |

  ```json
  { "submit_type": "ui", "param": null }
  ```

  ```json
  { "submit_type": "dialogue_injection", "param": "quest_submit" }
  ```

- `submit_type`、`param` 都不本地化。不再存提交标题、说明、按钮文案；旧的三文案配置及未知提交类型会明确报格式错误，不静默丢弃或猜测提交方式。UI 模式不接受空字符串、空对象等伪参数，对话模式不接受空白、带 `@` 或含空白的名称。对话名沿用 `.hs` 的注入点语法，PAK 导出通过现有 `hsInject` 接线检查引用存在性，名字大小写不敏感。
- **进度自身只描述一次提交**：提交进度时提交其 `goals[]` 中的全部 goal，而不是为每个 goal 选择方式、逐 goal 点击或只提交满足 `completion` 的子集。`completion` 继续描述完成条件，不缩小交付范围；实际整体提交是否成功由实例报告。进度内 goal 仍只保存 `{id, kind, params}`，不能含 `submission` / `submit_type` / `param` 等提交属性。目标节点的单个 `goal` 同样不描述入口，由目标节点自身描述。
- 目标持有的 goal 声明 `requires_delivery = True`，或进度的任意 goal 声明 True，却缺少该节点的 `submission` 时，表单诊断、图模拟和 PAK 导出报告配置错误；一个进度只报告一次缺少统一提交配置。仅满足条件表示“可以提交”，仍为运行中、Q 回 N；实际提交成功后才进入已成功并从成功口发一次 A，进度不会按 goal 数量重复广播。
- 交付拒绝或本次提交未完成不是 goal 失败：仍运行中，可重试，不发 A。goal 实例报告失败才进入已失败、从失败口发 A。成功、失败或关闭后均不能再提交。
- 图模拟器只提供“模拟提交成功 / 模拟提交未成功”外部结果注入；进度的成功结果代表其全部 goal 已整体提交。模拟器不执行 Python、打开真实任务 UI/对话、校验或扣除物品，也不承诺游戏交付的事务回滚。游戏侧加载器、UI/对话入口路由及实际交付仍由 Mod 接入，不能把模拟按钮当作实际交付实现。

### 2.4 逻辑节点

- 左端口两个：`input` **并且**、`input2` **或者**，均可多线；右端口 `output` 可多线。没有内容。
- 收到 **A**：开启一轮，向两个左端口发 **Q**；收齐应答后判定：
  - 并且端口（非空）要求**全部** A；或者端口（非空）要求**任一** A；
  - **所有非空端口都满足**才从右端口发 **A**；逻辑放行不产生 C，不消费输入；
  - 不满足则本轮静默结束；之后任一 A 重新开启一轮。
- 收 **C**：结束自身的推进轮次，向两个左端口转发 **C**；已经受理的独立 Q 查询仍完成应答，避免调用方永远等不到结果。
- 收 **Q**（右端口）：建立独立的只读查询，向两个左端口发送 Q；上游若仍是逻辑节点则继续逐层查询。收齐后按同样的「并且 / 或者」规则沿原请求连线回复 A 或 N，并恢复调用方的轮次标识。没有任何输入的逻辑回 N。
- Q 求值不广播激活、不发 C、不消费上游，也不锁存上次放行结果；每次重新读取上游在该轮投递时的回答。它与 A 驱动的推进轮次分离，多调用方和嵌套查询互不覆盖，重复或过期应答不得启动推进。
- 目标或条件节点直接或经过任意层逻辑节点接入「并且」端口时，针对该「并且」入线给出 **warning**：「非建议用法，可能导致任务挂起」。例如「目标 → 逻辑 A 的或者口 → 逻辑 B 的并且口」会在 A → B 连线上警告；上游使用「或者」不能屏蔽下游的风险。只穿透逻辑节点，遇到进度节点即停止追溯；汇合路径不重复警告。目标的成功口、失败口均适用，草稿连线也检查。这些节点不维持任务存活，作者需检查等待期间是否仍有能够到达结束节点的运行中进度。它不是非法连接，不阻止编辑、模拟或导出，不自动改接「或者」端口；「或者」的语义不同，应按设计选择。

逻辑之间允许串联：A 触发下一层推进，Q 对嵌套输入递归求值并沿原通道回复，C 逐层逆向传播。所有子查询与 A/N 应答仍走同一 FIFO 队列，服从单步、断点、终局、传播预算及故障回退规则；尚有子查询投递时不执行结算边界的自动失败检查。

此处「挂起」用于描述流程停滞风险，不表示已经实现 GM 修复与恢复机制；当前模拟器仍沿用 §9.4 的自动失败规则，本项警告不改变运行语义。

### 2.5 结束节点

- 两个左端口：`input` 成功入、`input2` 失败入，均可多线。
- 收 **A**：从哪个入口进来就记录哪种任务终局；第一个有效投递锁存整个 quest 的 `{endId,result}`，立即终止传播。尚未投递的信号进入丢弃记录，不再送达，不覆盖终局。
- 终局前已处理的状态保留；其他运行中进度直接标记为 `terminated`（随任务结束），不算失败，也不广播 C。此实例拒绝后续业务事件；只有重置才能重新运行。奖励只允许由胜出结局触发一次；模拟器不发放真实奖励。
- 内容：`title`（结局标题）与 `rewardKits`（奖励礼包引用列表）。
- 可以有很多个结束节点，也可以完全没有结束节点。缺少结束节点在语法上合法；没有任何**与开始联通**的结束节点是校验 warning，不阻止编辑。无结束节点的任务必定失败，开始后的首次信号结算边界按 §9.4 判定。

### 2.6 注释

- 存在 `layout.notes`，不是内容节点：不可连线。字段 `title` / `text` / `width` / `height` / `color`。

### 2.7 表单视图

- **双击节点**（或 Enter / F2）在画布上打开该节点的表单视图：一张更大的、没有端口的卡片，跟着画布平移缩放。
- **每个节点最多一张**：再次双击只保持原视图，不会开第二张；可以同时打开多个节点的视图。
- 视图可拖动，但位置只在**当前会话**有效，不写入 `.quest`、不参与校验、不进 Group、不可连线。
- 内容随改随写回文档（走工作区既有的撤销 / 保存）。
- 表单内容：进度标识符、两段日志、目标与完成判定、节点统一提交方式；开始进度额外包含可本地化的任务标题与说明；条件是可选标识符与判断规则组；目标是必填目标标识符、单个 goal 和节点提交方式。两类提交控件相同：无需提交 / UI / 对话注入点，只有对话类型显示参数输入。结束是结局标题与奖励礼包。逻辑没有表单。
- 节点正文与下方端口标签区分开布局，长标识符单行省略并可悬停查看全文；不显示重复的“双击编辑”提示，也不把表单关联锚点文字显示为业务端口。结束节点保留结局标题。
- 空白处右键「编辑任务信息…」等同于打开开始进度节点的表单。

## 3. 连线规则

- 来源必须有对应的右端口，目标必须有对应的左端口。
- **不能成环**：若从目标能顺向走回来源（含来源等于目标），连接被拒绝。
- 结束节点与条件没有出/入口的组合天然被端口表挡住（条件无左端口、结束无右端口、开始无左端口）。
- 幂等：同一条 `from`/`to`/`port`/`fromPort` 重复连接不会产生第二条线。

常见形态：

| 想表达 | 连法 |
|---|---|
| 进度后接一个阶段 | 进度`成功` → 逻辑`并且`；逻辑`通过` → 下一进度`激活` |
| 成功 / 失败分叉 | 进度`成功` / `失败` → 不同进度或结束节点 |
| 并且（全部满足） | 多个进度/条件 → 同一个逻辑的 `并且` |
| 或者（任一满足，其余作废） | 多个进度 → 同一个逻辑的 `或者` |
| 条件门 | 进度 → `并且`；条件 → `或者`（两个非空端口都要满足） |
| 任务终局 | 进度或逻辑 → 结束节点的 `成功入` / `失败入` |

## 4. 信号

| 记号 | `kind` | 方向 | 含义 |
|---|---|---|---|
| **A** | `activate` | 顺流 | 我被激活 / 我成立 / 这是我的结局 |
| **Q** | `query` | 逆流 | 你现在是什么状态？ |
| **C** | `cancel` | 逆流 | 这个消费者不要你了 |
| **N** | `none` | 逆流 | 对 Q 的否定应答；任何未特别说明的节点收 Q 都回 N |

- **顺流**：沿输出口 → 连线的目标输入口；**逆流**：沿输入口 → 连线的来源输出口。
- 线上只有这四种；成功与失败由**端口**区分，A 不携带原因。
- **C 的唯一主动来源**：普通进度收到 A，从未激活变为运行中时，向左端口产生 C。开始进度没有左端口，初始化不产生 C；重复激活、结算、Q 求值、逻辑放行及任务终局都不主动产生 C。逻辑与未激活进度只能转发收到的 C；运行中进度收到 C 后取消并停止转发，条件与目标关闭且停止转发，已结算进度忽略 C。

## 5. 进度状态机

```text
未激活 --A--> 运行中（并向左端口发 C） --结算--> 已成功 | 已失败
运行中 --C--> 已取消
未激活 --C--> 未激活（向上游转发 C）
已成功 / 已失败 / 已取消 --C--> 忽略
```

- 开始进度节点由「初始化任务」直接进入运行中（不走 A，也没有左端口可发 C）。
- A 只对**未激活**生效；其余状态幂等忽略。
- **激活即消费输入**：一次 A 会让左端口上的**所有**连线都收到 C。链式图里上游此时都已结算（C 被忽略），不影响推进；同一端口存在多个候选上游时，先激活的分支会消费掉其余候选（先到者赢）。
- 状态只在模拟器内存里，**不写进 `.quest`**。

## 6. 逻辑的一轮查询

```text
收到 A（触发） → 开启第 n 轮，向两个左端口发 Q（携带轮次号 n）
各输入回 A / N → 收齐本轮所有入线的应答后判定
满足 → 右端口发 A，本轮结束（不主动产生 C）
不满足 → 本轮结束（不发 C）；之后任一 A 重新开启第 n+1 轮
```

- 应答携带**轮次号**：上一轮的迟到应答会被吞掉，不会误开新一轮。
- N 表示「此刻不满足」，不表示「永远不」；之后结算时发出的 A 会被下一轮重新问到。
- 没有入线的逻辑收不到 A，永远不会放行。

## 7. 草稿节点

- 与 `start` **联通**的节点才是**生效节点**；其余是**草稿节点**。联通性把连线视为**无向边**——条件只有出边，按有向可达会永远判成草稿。
- 草稿节点在画布上变暗、带「草稿」徽标；校验给 warning；草稿条件允许预置真值，但初始化与之后的真值变动都不广播。
- 把草稿接进联通分量后立即转为生效。

## 8. 实例初始化

初始化发生在**首次接取**与**读档（load）**，同一实例只做一次（模拟器「重置模拟」后可以重做）：

```text
1. 开始进度节点与所有生效目标、条件节点一起进入运行中（已关闭的节点不重开）
2. 对每个生效条件按当前世界真值求值（不是用缓存）
3. 按节点 ID 的稳定顺序，为真值条件各广播一次 A
4. 运行信号队列
```

- **只广播已为真的条件**；假的什么都不发。
- 只播报**生效条件**（与开始进度联通）；草稿条件不参与。
- 稳定顺序保证同一存档重放结果一致。
- 初始化之后，条件只在 **假→真** 的上升沿增量广播；不再周期性扫描。
- 重复初始化是空操作；要重放需先重置实例。

引擎侧约束：条件节点的判断规则可以引用别的任务状态，所以**所有 quest 实例的状态应先全部加载完，再统一初始化和广播**；否则会按半加载状态广播出错误事实。

## 9. 信号顺序与终局边界

每次外部事件开启一个 `pulse`，期间不得插入其他事件。所有投递共用一个 FIFO 队列：取出队首，接收者原子地完成状态变化与判定，产生的投递追加到队尾。**入队不代表送达。** 单步恰好完成一条投递；动画阶段不允许另一投递插入节点判定。

### 9.1 局部分支顺序

顺序是从 `.quest` 当前布局实时推导的结果，**不持久化 `order` / `reverseOrder`**：

- 顺流排序的范围是同一源节点、同一输出端口；逆流排序的范围是同一目标节点、同一输入端口。
- 当前 quest 画布是横向布局：顺流按接收节点 **y、x** 排序，逆流按上游接收节点 **y、x** 排序；相同坐标按连线 ID 的 UTF-16 码元字典序比较（不使用 localeCompare）。这些序号不是全图执行排名。
- 每次查询顺序或渲染连线序号，都从当前文档位置计算，不改写源文档；移动节点只保存位置，因而可能改变执行结果。画布表单、注释位置及视口不参与排序。
- 缺布局的位置视为 `(0,0)`。旧图里的两个排序字段不再是权威，读取时移除，后续图编辑保存不再生成；不能用遗留字段覆盖当前布局。
- 任意重排 `logic.links` 数组不得改变运行结果。圆形序号显示在分支连线上；靠源端为顺流，靠目标端的淡色序号为逆流。
- 编译 `.questc` 时才固化为节点端口上的有序指针数组，数组顺序就是运行顺序；引擎不需要布局或重新排序。模拟期间锁定编辑；外部修改若改变任一方向顺序，进行中的传播故障回退，不能跑到一半换序。

### 9.2 生成顺序

初始化先让开始进度与全部生效目标、条件运行，再按条件 ID 的 UTF-16 顺序播报生效真条件；节点内部使用各端口的顺序。作者态从位置推导，编译态使用对应端口数组，两者结果一致。

| 投递 / 判定 | 新投递的入队顺序 |
|---|---|
| 逻辑收 A 开启查询 | `input` 的 Q，再 `input2` 的 Q；各端口按输入列表顺序 |
| 逻辑收齐本轮应答且放行 | 仅向下游发 A，不产生 C |
| 逻辑收到 C | 转发到 `input`，再 `input2`；各端口按输入列表顺序 |
| 进度收 A | 变为运行中，然后从 `input` 按输入列表顺序发 C |
| 进度收 C 且未激活 | 向 `input` 按输入列表顺序转发 C |
| 进度结算 | 先改自身状态，再从对应出口按输出列表顺序发 A |
| 目标结算 | 先进入已成功或已失败，再从对应出口按输出列表顺序发一次 A；收到 C 后进入已关闭 |
| 条件变真 | 从 `output` 按输出列表顺序发 A |
| 结束节点收 A | 锁存唯一终局，终止本次传播，剩余队列全部丢弃 |

Q 的应答沿原通道回到发起方，并携带查询轮次。相同轮次、相同连线的第一个应答被记录；重复和迟到应答不能覆盖已经记录的值或启动新查询轮次。

递归逻辑查询另带仅运行时使用的 `queryId`（该次 Q 的投递编号），与推进轮次隔离。内部子查询使用自己的标识，回复上一层时恢复原请求的 `round` / `queryId`。每个请求独立汇总，不把应答发往其他输出线；完成后删除临时记录。响应保留原 Q 及全部输入应答的因果来源，调试记录区分只读求值和推进判定。这些字段不写入 `.quest`，预算或图变更故障时与其他状态一起回退。

**不同外部事件的先后仍然是业务语义。** 位置序号只确定一次 fanout 内的顺序，不会让队列深处的“高优先级”信号跳到队首。若作者希望多个分支均完成才结束，必须在结束节点前显式汇合；终局不会等待队列排空。

### 9.3 执行安全契约

- 运行图最多 **512 个业务节点、4096 条连线、每端口 128 条连线**；禁止环、重复连线与非法端口。模拟运行及多进度导出都检查，超限拒绝执行/导出。
- 同一 pulse 中，相同接收节点、接收端口、进度状态和逻辑轮次的 C 只处理一次；重复 C 记录为忽略，避免菱形反复展开取消。状态改变或新的查询轮次是不同的处理目标。该去重集合不会跨 pulse 保留。
- 每个 pulse 预算为 `min(250000, max(512, 边数×128 + 业务节点数×32))`，同时限制已处理数与排队/新产生的总数。它是明确的资源限制，**不是所有 DAG 必定能执行完的数学上界**。仅通过结构校验并不免除预算保护。
- 耗尽预算产生 `budget-exceeded` 故障；整次外部事件的进度、目标、条件、查询、终局和初始化状态回退到事件前检查点。保留调试轨迹并清空待执行队列，重置后才允许继续。不能把部分执行结果当成正常完成。
- 终局与故障不同：正常终局提交终局之前已经发生的变化，丢弃未投递信号；预算故障回退本次事件全部业务变化。
- 传播期间图发生变化也必须停止，不能把旧队列继续送进新图。当前 UI 在初始化后锁定编辑，外部文档变化时停止播放并重置本地模拟。
- 将来引擎接入奖励、脚本等外部副作用时，须在本次传播成功后再提交这些效果，并保证终局奖励幂等；不能依赖模拟器内存回退来撤销外部副作用。

### 9.4 信号结算后的自动失败约定

本节是已确定的运行契约：每轮信号传播完整结算后，任务若**已经开始、尚无终局且没有执行故障**，在以下任一情形下自动失败：

1. 图内没有运行中的进度节点；
2. 所有运行中的进度节点，都无法沿业务连线的正向到达任意结束节点的成功入或失败入。

运行中的进度包括开始进度。只要至少一个运行中的进度在结构上能够正向到达结束节点，就不触发这条兜底；这不保证其未来一定能通过逻辑条件或实际到达终局。

目标节点的运行状态不计入这项检查；它与条件都不能续命，终局后也不能用目标结算恢复任务。本轮目标已经发出的信号仍先结算完，再检查自动失败。

- **判定时机**：一个外部事件产生的全部 A/Q/C/N 及其后续投递均已处理，FIFO 队列为空时判定；初始化、结算或事件没有产生任何投递时，也立即经过这个结算边界。单步中途、动画等待、手动暂停及断点暂停均不算结算完成，不能提前判失败。
- **正向可达性**：从运行中进度的成功或失败输出口出发，沿 `from → to` 的业务连线、经过中间节点到结束输入口。按图中既有边做结构检查，不根据未来状态删边，也不预测中间进度或逻辑将来能否满足。不能逆走 Q/C，也不能用画布坐标或草稿判定所用的无向联通代替。
- **条件不延长任务存活**：不等待条件未来变真。即使某个条件未来可能发 A 并激活进度或触发结束，当前结算边界满足上述失败条件时仍立即失败。失败后不能由后续条件变化恢复；条件在本轮信号传播中已经发出的投递，仍须先按 FIFO 处理完。
- **显式终局优先**：若本轮已有有效 A 到达结束节点，沿用 first-wins 的成功或失败终局，不再执行自动失败兜底，也不覆盖已有终局。
- **无结束节点**：语法合法，但没有任何运行中进度能到达结束节点。因此任务开始后，在首次结算边界自动失败，不等待开始进度结算。未开始的图不会仅因结构不完整而产生运行时失败。
- **无出连线的进度**：语法合法，可以与仍能到达结束节点的主线并存。只要主线仍有符合条件的运行中进度，就不会因附加分支无出口而自动失败；主线失去这种进度后，附加分支仍在运行也不能阻止失败。
- **失败效果**：记录任务失败及原因（「没有运行中的进度」或「运行中的进度均无法到达结束节点」），将剩余运行中进度按任务终止规则标记为 `terminated`，不广播 C。不虚构结束节点，不触发任何结束节点的奖励；此实例拒绝后续业务事件，重置后才可重跑。
- **故障不是自动失败**：预算耗尽、非法图或传播期间图变化仍按执行故障处理，不将回退后的空队列冒充任务失败。

模拟器已在每轮信号结算边界执行本节判定，包括初始化或结算没有产生投递的情形。自动失败的终局使用 `endId: null` 和失败原因区分于显式结束节点；调试栏在收起时也显示失败原因，并始终提供「重置模拟」。

## 10. 可视化模拟器

底部调试栏包含：初始化、单步、播放/暂停、速度（慢速/正常/快速/无动画）、重置、实例终局或故障。初始化前可预置条件；初始化后锁定图编辑，重置恢复编辑能力。

工具栏提供默认开启的「自动播放」，收起详情时也可操作。开启后，初始化、进度/目标结算或条件变真产生的新队列自动按所选速度播放；没有信号时保持等待。关闭会暂停当前播放，之后新事件保留队列供单步或手动播放。手动暂停、单步、断点和运行到目标仍正常停止，重新开启自动播放不会擅自恢复已暂停的队列，需按「播放」继续。模式只属于当前画布会话，不写入 `.quest`，重置模拟保留该选择。

- **待投递**：队首突出显示，列出 A/Q/C/N、发送者、接收者、端口、查询轮次；点击定位接收节点并选中对应连线。
- **已处理**：区分接收与忽略，并记录原因。历史在新 pulse 开始时保留最近 4000 条，再追加本次受预算限制的轨迹。
- **已丢弃**：终局后的未送达信号及故障中止的剩余信号独立列出，不冒充已处理。
- **详情**：可选中任意历史或队列投递，查看当时是否接收、产生几条新信号、哪些节点状态发生变化；默认跟随最近已处理投递。长列表使用固定行高的虚拟滚动，可滚动检查全部保留记录。
- **画布**：A 绿、Q 蓝、C 橙、N 紫，始终同时显示字母；Q/C 逆流，查询应答沿原通道顺流。节点描边突出最后一次接收或忽略。
- 动画只呈现执行顺序。暂停不继续投递；切到非活动工作区停止播放。无动画仍逐条执行，每条让出浏览器事件循环，结果与单步/带动画一致。
- Ctrl 点击未初始化的开始进度进行初始化；初始化后 Ctrl 点击运行中的进度或目标结算成功（Shift 为失败），也可在节点右键菜单结算；Ctrl 点击条件切换真值。传播未完成时不接受新事件，终局/故障后必须先重置。
- 队列、日志、播放速度、终局及故障均是本地模拟状态，不写 `.quest`，不提交协作事务。连线顺序也是派生结果；只在 `.questc` 中由端口数组固化。

验证入口：`npm run test:quest-signals`、`npm run test:quest-simulator:ui`、`npm run test:progress`、`npm run test:quest-compile`。浏览器截图保存在 `node_modules/.cache/quest-simulator/`。

### 10.1 断点与运行到节点

- 右键业务节点选择「添加节点断点」，或右键连线选择「添加连线断点」；再次操作移除。节点上显示红点，连线显示红色底描边。断点仅在本地组件内存中，不保存到 `.quest`、不参与协作提交。
- 节点断点检查**队首接收者**，包括 A/Q/C/N；连线断点检查队首通道，包括正向与逆向投递。它们在实际投递及状态变化之前暂停，不插入或重排信号。
- 第一次播放命中队首断点必须停下；只有已经停在该投递上，再按播放才忽略**当前投递编号一次**。同一节点或连线的后续新投递仍会断下。单步始终允许处理队首一条。
- 有待处理信号时，右键节点「运行到此节点」：沿原队列继续，到目标接收前暂停；目标是一次性的，不创建永久断点。若本轮排空而未到达，明确报告未到达；不自动结算其他进度来追赶目标。
- 重置模拟保留断点以便重复调试；清除按钮移除全部断点。切换文档清空；图编辑或外部更新删除节点/连线时清理失效断点，并停止当前运行到目标。

### 10.2 投递身份与因果记录

每条入队投递分配模拟实例内单调递增的 `traceId`，携带外部事件 `eventId`、直接父投递 `parentId`。初始化、结算、条件变真等事件单独记录说明。多个 fanout 子投递具有不同编号、相同父编号。编号为本机调试身份，不是节点 ID、持久存档编号或网络事务 ID。

- 逻辑放行的 A 除直接触发父投递外，还带本轮各条输入应答的 `causes`，不能只把放行归因于最后到达的一条应答。后续 C 必须来自普通进度的首次激活，逻辑只能转发已有 C，因果链保留每一跳来源。
- 查询的 A/N 应答直接引用对应 Q，并保留查询轮次。收齐时记录并且/或者是否满足、各通道的 A/N 和对应投递编号，未放行的轮次也可检查。
- 已处理记录保存当时的状态变化、产生的子投递和判定说明；后续结算不会把历史详情替换成节点当前状态。预算故障中已执行的记录标记「已回退」，不能冒充生效结果。
- 点击列表项定位节点/连线并检查该条记录；点击来源、参与应答或子投递可继续跳转。因果面板一次列出最多 32 个祖先，可点击继续追溯。父记录已被历史保留上限裁剪时显示缺失，不推测或重新绑定到同号记录。
- 支持按 A/Q/C/N、仅忽略、节点名称或 `#投递编号` 筛选。检查的投递可独立于当前筛选结果，使用「跟随最新投递」回到实时观察。
- 停顿、筛选、定位、检查记录和动画速度都只是观察行为；不能改变投递身份、FIFO 顺序、终局或业务状态。所有这些诊断元数据都不导出到 PAK。

验证：`npm run test:quest-debugging` 覆盖因果身份、查询证据、历史不变性、故障标记和断点观察不变性；`npm run test:quest-simulator:ui` 实际验证节点/连线断点、继续、逆向断点、历史父子跳转、筛选与运行到目标。

## 11. 校验清单

**结构解析失败**：格式/版本不符、`start` 缺失或指向不存在的进度、`progress` 不是对象、节点 ID 跨集合重复、`FlowText` 带 `key`、旧草稿字段（`entry` / `nodes` / `goals` / 根级 `name` / `description` 等）、逻辑/结束带旧内容。

**语义 error**：超出图/端口规模限制、重复连线；开始进度不存在；连线端点不存在或端口不对；成环；Group 引用不存在的节点 / 重复分组；进度内目标 ID 为空或重复；进度或目标标识符为空、任意非空节点标识符重复；goal 交付声明错误或类型冲突；交付型 goal 所属节点缺少提交配置，或对话注入点名为空/格式无效。未知提交类型、参数类型不符、旧三文案配置、在内嵌 goal 上配置提交会结构解析失败；导出接线另检查注入点是否存在。

**warning**：任务未命名；草稿节点；没有任何与开始联通的结束节点；进度内目标未选类型；条件节点未配置规则（恒假）或规则缺少对象；目标或条件节点接入逻辑的「并且」端口（非建议用法，可能导致任务挂起）。
