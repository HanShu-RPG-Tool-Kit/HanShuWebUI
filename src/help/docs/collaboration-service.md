# 工程服务与多人协作

React 是 C，Rust 工程服务是 S。连接 S 就是打开一个完整工程，剧本、进度、流程图、脚本、物品、礼包、导航器、资产与皮肤工作区使用同一工程会话。原来的独立「共享进度」入口已移除。

## 权威边界

- S 持有普通工程目录，维护主体、会话、授权、写权与文件版本。所有工程创建、保存、覆盖、改名、移动和删除都由 S 执行。
- C 不持有工程目录的 OS 文件系统句柄。`ProjectDirectory` 是只读的远程目录引用，不含 `createWritable`、`removeEntry` 或任意本机路径打开能力。写入通过明确的 HTTP 工程命令请求。
- 浏览器本地存储、IndexedDB 是草稿与缓存，不能直接覆盖服务端工程。资产缓存按页面运行实例隔离，同窗口工作区共享；同浏览器多个标签页不会互相读写未保存草稿。文件导入只读取用户选择的文件；导出下载到客户端，不能指定服务端绝对路径。
- 桌面版运行同一 S。选择本机工程目录的对话框由可信的 Rust 宿主弹出，返回服务连接信息；C 不获得目录写权限。旧皮肤库写入 IPC 与 WebView 文件读写自动授权已移除，原生网络辅助仍可用于下载皮肤。

## 主体、会话与授权

Subject 是身份主体，包含 `id/name/kind/enabled`，可表示自然人、agent、服务或工具。凭证登录建立 Session；同一主体打开两个客户端，会得到两个独立会话。

工程角色为 owner/editor/viewer。owner 创建主体、调整授权、停用主体和接管写权；editor 修改资源；viewer 读取资源。权限由 S 检查，绕过界面直接请求也不会获得写入能力。目前采用管理者签发的高熵凭证，不提供密码注册、密码找回或第三方登录。以后可增加认证入口，继续复用同一主体与工程授权。

会话令牌只保存在内存，不写 URL 或持久化浏览器存储。会话有效期 60 秒，客户端每 8 秒心跳；服务重启后重新登录。管理者恢复凭证仅位于 S 的私有目录，HTTP 不返回它；新主体凭证仅创建时返回一次。

## 工程目录

```text
工程根/
  project.json                 # 原工程清单，不是服务身份数据库
  src/                         # .hs/.char/.py/.progress/.hflow/.nav/.item/.kit
  meta/                        # 创作资料与配音服务配置
  assets/                      # 语言、图片、音频等
  .hanshu/
    skinmanager/               # 皮肤集合与对象文件
    service/                   # S 私有状态，不经资源 API 暴露
      project.json             # 主体、授权、凭证哈希
      owner-key
      service.lock
      file-undo.json           # 事务期间存在的撤销记录与提交决议
      file-transactions/archive/ # 按事务编号哈希分片的不可变 gzip 回执；查询按主体授权
      history/                 # 工程历史：对象、版本清单、命名标签，按当前工程授权查询
      write-staging/           # 私有原子替换暂存区
```

S 打开普通工程目录，直接读写这些资源，不需要把进度文件另外导入一份独立数据库。原型第一版的独立协作数据库不作为普通目录工程自动兼容。

仅允许访问工程清单、`src`、`meta`、`assets`、`.hanshu/skinmanager`。S 拒绝绝对路径、`..`、Windows 设备名/ADS、大小写冲突、符号链接/目录联接，以及服务私有目录。工程目录同时只能由一个 S 进程管理。

## 修改与一致性

每个文件的版本是其内容哈希，目录版本包含整个子树。C 提交读取时的版本，S 同时验证会话、权限、写权与版本；409/423 不会自动改用新版本重试覆盖。

写权属于会话，30 秒有效并随心跳续租。`.progress` 使用明确的「开始编辑／结束编辑」会话；其他编辑器仍在提交时申请写权。文件事务申请的临时写权在请求结束后释放，已经由其他操作或显式编辑会话持有的写权保持原样。不同资源可由不同会话同时持有；同一资源的未提交本地编辑仍是草稿，只有有效写权持有者能提交。

当前编辑策略要求修改语言、配音时同时持有源文档写权，防止两个人分别修改 `.progress` 和它的标题语言文件。这是可替换的操作策略，不是归属关系的固有含义。S 为改名/移动/删除推导应联动的归属资源，并检查事务完整性。目录操作也检查子树中的写权。

### 资源关系与操作策略

资源关系、操作策略和事务执行分为三层，第一版规则直接定义在 Rust 中。

| 层 | 开发入口 | 职责 |
| --- | --- | --- |
| 关系解析 | `project-core/src/resource_relations.rs` | 从资源类型和工程目录识别归属与引用；关系本身不取得写权、不执行联动 |
| 操作策略 | `project-core/src/resource_policy.rs` | 根据操作推导文件动作、编辑权威路径、需要的租约和关联范围 |
| 执行 | `project-core/src/files.rs`、`file_transactions.rs` | 提交时重算策略，检查完整性、主体权限、租约、版本，并原子执行或拒绝 |

归属用 `ownership` 表示：`.hs/.char/.progress/.hflow/.nav/.kit/.item` 与各语种语言文件、配音目录之间的关系。引用用 `reference` 表示；第一版解析 `.progress.rewardKits` 到礼包源文件的引用。关系带 `role`（`language/voice/rewardKit`）、`from`（源）、`to`（目标）。有效路径的悬空礼包引用仍作为关系返回；不合法引用和无法解析的源码内容不会使整个工程的关系查询失败。

| 请求 | 当前策略 |
| --- | --- |
| 写入普通资源 | 只写请求的文件，取得其路径写权 |
| 写入语言或配音 | 只写请求的文件，同时要求文件与源文档写权；不自动重写源文件或其他语种 |
| 源文件改名/移动 | 联动已有的各语种语言与配音，要求源路径、目标路径及对应编辑权威路径的写权 |
| 删除源文件 | 联动它拥有的语言与配音；引用的礼包保留 |
| 移动/删除包含源文件的目录 | 展开目录内各源文件需要联动的资源，不遗漏目录外的语言和配音 |
| 引用礼包 | 仅表达引用，不自动锁定、移动、删除或重写礼包 |

低层 `/api/files/leases` 现在只申请传入的路径租约，不隐式展开关联。C 应先查询操作计划，再申请 `leasePaths`。即使 C 绕过查询或只申请部分路径，S 也会在提交时重新推导策略并拒绝缺失写权或关联动作的事务。路径写互斥、祖先/后代路径冲突、续租与接管机制继续复用。

计划包含 `revision`、展开后的 `operations`、`leasePaths`、`authorities` 和相关 `relations`。每项动作携带读时观察到的 `version/destinationVersion`，以及产生该动作的原始请求路径 `originPath`；`authorities` 给出路径对应的 `authorityPath/sourceKind`。计划是查询结果，不是保留资源的凭证：查询与提交之间可以发生其他修改，提交必须重新校验。C 保存已有草稿时继续使用草稿原版本，不能把计划里的最新版本当作自动合并或覆盖授权。

C 的 `ProjectClient.planOperations` 是操作计划入口；`resourceRelations` 可单独查询关系。进度编辑权限、关联草稿检查、结构操作的动作与写权范围使用 S 返回的信息，不在 C 复制目录正则。编辑器仍负责决定本次业务修改的内容，并把正文、语言、外链资源的实际修改收集成一批；查询到引用不会自动把外链文件加入修改集。

当前规则没有提供独立语种编辑、自动修复引用或删除引用目标前的交互确认；这些需要分别调整编辑/删除策略和界面。也没有通用关系数据库、可编辑规则或插件系统。解析目前随请求扫描工程，适用于现有小规模工程限制。

配音子目录按实际源文件的最长路径前缀解析归属。如果一个待级联目录还包含其他源文件的配音，而这些源没有参与同一兼容操作，S 拒绝单独级联。新建或移入源文件也不能悄悄改变已有配音的归属。这类重组需要以后设计明确的迁移操作。源文件移动必须保留资源类型，普通文件不能通过改名进入源文件类型、绕过其内容校验。

### 资源协作栏

剧本、流程和进度文件、皮肤库共用顶部头像与保存状态栏。头像颜色和缩写来自主体，点击可查看本端名称、角色与状态；同一主体的不同窗口分开显示。皮肤按固定选中的条目显示协作者，悬停预览不会改变在线焦点。

「查看中／编辑中」与实际写权分开表达。剧本、流程和皮肤的编辑状态是 C 上报的编辑意图，由 S 按角色校验；只读主体不能声明编辑。它不申请写权，也不保证提交一定成功。已有锁策略保持不变：普通文件和皮肤提交时申请临时写权，进度仍需明确开始编辑并持续持有写权。进度的编辑状态继续由 S 根据实际写权推导。

- 打开进度先进入查看模式，不申请写权，也不自动迁移正文或写入语言默认值。点击「开始编辑」取得源文档写权后才能修改表单。
- 「结束编辑」仅释放这个文件的显式写权，保留本窗口未保存草稿。另一端随后可以开始编辑。管理者可点击「接管编辑」并确认；原编辑端转为只读，草稿不被删除。
- 切换文件或工作区会更新正在查看的对象；没有活动资源时清除查看标记。已申请的编辑写权保留，便于来回切换文件；可用「结束编辑」或工程栏「释放全部写权」主动交接。
- 断线、降为只读或写权丢失后暂停表单编辑。重连不会自动夺回写权，需要点击「重新申请写权」。保存与原提交重试也不能绕过这个步骤；已提交事务的结果查询不要求重新申请。
- 标题、描述等语言草稿与正文遵守同一编辑会话。重新取得写权不改变草稿的原版本；若其他人已保存，后续提交仍进入版本冲突处理。

头像表示最后一次上报的文件焦点，不表示逐字符光标位置。浏览器直接退出或网络中断而不能发送离开通知时，S 在会话 60 秒有效期结束后移除头像，写权按 30 秒租期释放。焦点发布有活动视图归属保护，隐藏工作区的刷新或卸载不能清除新工作区的焦点。断线保留草稿，恢复连接后重新上报当前焦点；这不会自动申请写权。

状态栏按当前文件及其归属资源匹配提交；皮肤按命令内的条目身份匹配，另一条皮肤的失败不会显示到当前条目。新建、移动、批量标签和导入弹窗跟踪实际产生的提交编号，在操作现场查询结果或重试原请求。普通文件冲突在现场打开原有版本对照界面；皮肤条目沿用详情中的字段恢复，管理命令须明确放弃原操作并刷新后再重新确认。未知结果不能放弃或换新请求重发。全局提交记录与现场入口操作同一事务。

文件事务先校验整批修改，再保存撤销日志、执行原子文件替换，最后持久化提交决议和回执。执行失败尝试回滚；没有提交决议的日志在重启时回滚，有提交决议的日志只补全回执，不重复移动或删除。恢复失败则拒绝继续提供文件操作。临时替换文件位于 S 私有目录，不进入工程资源树。逐文件原子替换与恢复日志保护的是经 S 访问的工程，不向绕过 S 的磁盘读取程序承诺跨文件原子视图；当前测试覆盖进程中断恢复，没有宣称硬件断电下的全盘持久性保证。

保存只提交变更，不根据客户端清单中缺少的条目删除文件，也不整树删除后重写 `assets`。删除是显式命令。`.progress` 执行结构校验，皮肤库索引检查基本结构；普通源码可以保留未完成内容，S 不执行目标定义或游戏脚本。

### 客户端编辑事务

C 的 `EditTransactions` 协调一次操作的变更集，不在 C 另建“逻辑文档”模型。编辑器决定实际修改的内容，资源归属与结构联动由 S 的关系和策略层解析，S 继续负责写权、版本校验和批量落盘。外链共享资源只在实际被修改时进入变更集，不因为被引用就自动加入。

剧本与进度编辑器中的语言修改先暂存为草稿，不再单独自动提交。Ctrl+S 或全局「保存修改」等待语言缓存写入及资源登记完成，收集当前工程的全部已修改正文、语言和资产，再发送一个批量事务。收集期间若继续编辑，重新收集以避免正文和语言来自不同草稿时刻；提交期间产生的新草稿保留为下一次待保存内容。不同路径的本地语言镜像可独立准备，同一路径按顺序写入，准备失败则不发送这次保存。

工程栏显示待保存、准备、提交、失败与冲突，并提供提交记录、原提交重试和提交备份导出。失败记录保留原内容和原版本；重试不会重新收集新输入或采用远端最新版本覆盖。相关路径存在未处理失败时，不允许另一提交绕过它，不相关资源仍可提交。皮肤单条修改进一步按条目区分：同一索引内另一条皮肤可继续提交，整库操作仍与所有未处理条目修改互斥。「移除记录，保留草稿」只移除确定失败的记录，不改变草稿和版本；未知结果必须先查询，不能直接移除。

每次发送前，将完整修改快照（包括二进制）、原版本和 `transactionId` 保存到 IndexedDB。存储失败则不发送。回执按主体绑定，不绑定旧会话；重新登录后仍能查询自己的结果。确定拒绝后的重试使用新编号，结果未知时保留原编号和原请求内容，先查询回执再决定是否重发。仅 leaseId 可随新会话变化。原编号用于不同内容时 S 拒绝。点击「查询提交结果」只查询，点击「重试原提交」在没有回执时可重发同一请求。S 已提交的移动、删除不会重复执行。

版本冲突提供三栏对照：原始版本、服务器版本、本次提交内容。每个资源可采用服务器版本或保留本地修改，文本写入还可手动合并。移动和目标写入作为一个联动决定。提交处理结果时，所有修改仍是一批；采用服务器的路径转换为 `check`，与写入一起校验版本。对话框打开后服务器再次变化，整批拒绝，需重新载入版本再处理。二进制不尝试文本合并，可导出原提交备份。结果确认后更新缓存与各编辑器；确认期间产生的新草稿保留，历史回执也不会覆盖他人随后提交的新版本。

改名/删除之前若该源文件还有暂存的关联资源修改，先要求保存，避免草稿在旧路径被重新创建。其他资源操作经 `ProjectClient.apply` 进入同一事务队列和状态记录；具体编辑器仍需显式把业务上不可分开的修改组成一个批次，并非相邻的多次调用自动合并。

配音替换把 `.ogg` 写入和同键 `.ref` 删除组成一批；批量设置引用、批量删除各自组成一批。剧本与进度多选改名／删除先由 S 推导所有关联项，再整批执行。皮肤索引修改串行化，导入对象与索引一起保存；垃圾清理带索引版本检查。上述操作在 S 确认后才改变本地资源列表，重试成功也会补做本地投影。多键音频导入、TTS 和批量皮肤导入按条目提交，允许取消和部分成功，每个条目内部原子化。普通资产导入仍是草稿，随工程保存。

开发入口为 `src/project/editTransactions.ts`。`prepareDraft(path, run)` 登记产生草稿之前的异步初始化，例如新建流程的默认语言加载；`stageWrite(edit, prepare)` 暂存文件及其异步本地镜像；`submit(label, collect, true)` 等待初始化和镜像完成，再合并暂存修改。独立操作使用 `ProjectClient.apply(edits, label)` 显式提交一批文件。`npm run test:edit-transactions` 验证准备失败、收集时继续编辑、提交时继续编辑、原版本重试和语言合批。

WebSocket 通知文件版本与主体/写权状态，不广播全部正文。C 按版本读取变化，更新未修改的资源，保留本地修改。窗口内的源文件正文和暂存语言草稿保存在 sessionStorage，并携带原版本；重连不会把旧草稿自动覆盖到 S。待处理事务及其完整二进制快照持久保存在 IndexedDB，作用域为工程 ID、主体 ID 和窗口 ID；刷新同一窗口并重连会恢复。恢复不会自动提交。会话令牌不进入日志。尚未开始提交的二进制修改仍属于缓存草稿；尚无提交备份自动导入入口。清除浏览器站点数据会删除本地草稿和待处理记录；可通过「导出此提交」另存备份。

### 皮肤条目编辑与草稿

单条皮肤的名称、标签、模型、来源等修改使用 `skin-entry-patch`，由 S 在最新索引上检查目标条目的 `revision` 并应用指定字段。导入、文件夹、全库标签和批量管理使用 `skin-library-command`，C 提交用户操作及其读取基准，由 S 校验并修改当前索引。修改不相关的皮肤不会使这些操作因整个索引哈希变化而失效。索引依然短时持有文件写权，不承诺同时获得锁；锁冲突时保留原命令并允许重试。

| 皮肤操作 | S 校验范围 |
| --- | --- |
| 导入 | 固定条目身份、目标文件夹、自定义 ID、对象内容与引用；对象和条目同一事务保存 |
| 批量修改／删除 | 每个选中条目的身份和读取时修订号，整批成功或整批拒绝 |
| 文件夹改名／移动／删除 | 操作开始时的文件夹节点快照；删除仅允许空文件夹，移动校验父目录和环 |
| 同级排序 | 完整的同级文件夹快照，防止漏掉后来加入或移动的文件夹 |
| 重命名／删除全库标签 | 全部匹配条目的集合及修订号，范围变化时拒绝 |
| 清空文件夹中的皮肤 | 完整子树文件夹快照、条目集合及修订号；保留文件夹节点 |

勾选条目时保存可见的修订号，远端刷新不会替换勾选基准。打开移动弹窗后也不会自动更新目标条目的预期版本。清空文件夹的确认界面先读取完整范围；分页期间库修订变化则停止，确认后的新增、移入或修改由 S 再次检查。文件夹批量启用／禁用作为一个批次提交，一次最多 4096 条，超过上限不拆成静默的部分成功。

新建、改名和移动失败时弹窗保留输入与选择，并显示错误。写权占用可重试原请求；版本或范围冲突必须先放弃原操作、刷新并重新核对对象，不能进入 JSON 全文覆盖界面。未知结果只能查询或重放原请求，不能直接移除。导入行冻结首次提交的参数与条目身份；更改全局默认值不会改变原导入重试，查询或重放使用回执中的原始结果，避免成功响应丢失后重复创建条目。

导入校验结果及来源属于 C 的窗口状态，不再写共享 `tmp/import-jobs.json`。同一窗口的全部准备结果保留在内存中，远端索引更新重建皮肤会话时仍可继续入库；最近 50 条还尝试写入按服务地址、工程和主体隔离的 sessionStorage。存储满或不可用不会产生 S 侧提交失败，当前窗口的内存结果继续可用。完整刷新后不自动还原导入弹窗的行选择和参数；已提交操作的完整内容、对象字节和身份继续由 IndexedDB 事务日志负责恢复。

详情表单保存读取时的条目、当前输入及待确认修改。远端更新遇到干净表单时刷新；遇到本地草稿时保留输入和焦点，显示远端变化。用户可明确采用远端或保留自己修改的字段重新提交；重新提交携带确认时的条目修订号，远端再次变化仍会被拒绝。语义命令不进入整个 JSON 文件的通用冲突覆盖流程。

同一详情表单的提交串行处理。保存期间继续输入的字段保留，早先回执只确认对应的一次修改。S 回执保存当时的完整条目结果，因此丢失响应后查询原事务也能正确确认草稿，不拿后来读到的内容冒充原提交结果。未提交表单输入保存在本窗口 sessionStorage，作用域包括服务地址、工程和主体；切换条目、刷新及重新连接后可以恢复，恢复不自动提交。关闭窗口或清除站点存储可能清除这些未提交草稿；已发送命令仍按前述 IndexedDB 事务日志恢复。

皮肤索引的内存快照显式绑定读取时的内容哈希。条目命令成功不能自动提升旧整库草稿的版本；后续整库操作先取得匹配的正文与版本。生成的预览图片只缓存为本地 URL，查看皮肤不再因自动写共享 PNG 缓存而产生提交冲突。

V5 索引的整库写入也要保持条目修订号有效：保留条目的内容发生变化时必须递增其修订号，修订号不能回退。文件夹修复和缺省字段规范化同样推进受影响条目的版本。S 只校验并拒绝不合法候选，不改写 C 提交的字节；整库旧草稿若因此无法直接覆盖，应重新读取皮肤库后重做相应操作。当前 C 初始化只接受 schema 5，不自动修复或迁移旧索引；旧版转换需要单独完成。

## 手工验收路径

1. 用三个浏览器窗口打开同一个工程，其中两个使用同一主体。打开同一份进度，应看到三个独立胶囊、表单只读，S 没有因此创建写权。
2. A 开始编辑，修改标题但不保存；B 应显示 A 编辑中且不能开始。A 结束编辑后草稿仍在；B 取得写权修改并保存，再结束编辑。
3. A 重新申请写权并保存旧草稿，应出现版本冲突。对比三栏后，可将一份资源采用服务器，另一份手动合并，再一次提交。若处理期间失去写权，先关闭冲突对话框、重新申请，再继续处理；版本检查仍由 S 整批执行。
4. 管理者接管正在编辑的文件，原端表单应暂停且草稿保持。断线重连、降为只读也应暂停，不能靠保存按钮自动夺回写权。切换工作区后该窗口的查看胶囊消失，但不要释放其他文件的显式编辑写权。
5. 使用下方网络脚本复现截断响应、重新登录、刷新和重复移动／删除。未知结果记录应允许查询，原提交编号保持不变；服务已完成的操作不会重复执行。
6. 复制一个仍有待确认提交的标签页：复制页应取得独立的提交记录作用域，原页刷新后仍可查询原记录。普通标题和语言草稿可以被浏览器复制为独立草稿，但两个页面的后续缓存写入互不影响。

## 工程历史

「工程历史」是所有工作区共用的 S 功能，涵盖工程清单、源文件、创作资料、语言、音频、图片和皮肤库。浏览器缓存、草稿、在线状态、主体凭证和服务私有文件不进入内容历史。首次启用时建立当前工程的基线，不能补出此前未记录的编辑过程。

### 记录频率与展示

每次成功且确实改变内容的事务立即保存一个不可变版本。一次正文与语言合批只产生一个版本；失败请求、相同内容、原事务重试和仅申请写权不会增加版本。内容历史与工程落盘、提交回执共用同一个持久提交决议，崩溃恢复不会把成功提交的历史漏掉或重复执行恢复。

界面将普通连续编辑聚合为时段：相邻提交间隔不足 30 秒且当前时段未满 5 分钟时归入同组；超过任一边界开始下一组。分组不延迟落盘，也不丢弃组内的版本或各协作者记录。删除、改名/移动、恢复和皮肤批量管理操作形成独立记录。命名版本固定指向选中的准确序号，后来编辑不会改变它的内容；命名不另造内容版本。

历史列表提供分页、当前资源筛选、协作者和时间、容量统计。源资源筛选包含其所属语言、配音，排除引用的共享礼包；源文件和所属文件改名后可沿 S 记录的移动继续查询。对比的两侧都是已确认的历史版本，不读取未提交草稿。文本显示差异，二进制显示元信息，支持图片预览和下载；超过 2 MiB 的文件从界面下载查看。

### 恢复与权限

viewer 可以查看和下载；editor/owner 可以命名版本、恢复资源。editor 一次选择一个资源根，允许包含其归属资源；显式选择多个资源根或恢复整个工程仅允许 owner，不能通过传入所有根目录绕过限制。恢复先由 S 生成操作预览，列出新增、覆盖、删除、重建目录和关联范围，再由用户确认。普通文件可选择是否包含归属资源；引用礼包不自动跟随。皮肤可恢复单个条目及缺失对象，保留其他条目的当前修改，恢复后的修订号高于历史高水位。

恢复是新事务，不回退服务身份、授权、回执或历史。当前首版预览用整个内容树的指纹校验：预览之后即使无关文件有更新，也要重新预览；不能把旧计划直接覆盖到新状态。执行时重新计算操作策略并短暂取得所需写权，拒绝与其他主体持有的写权冲突。客户端保护本地草稿，成功恢复后只刷新可安全更新的内容。

恢复沿用事务协调层的原请求编号和持久回执。成功响应丢失时显示「结果待确认」，先查询或重试原提交；结果未明确前不能放弃并重新创建恢复。已明确的版本冲突应重新预览，不能把恢复命令当作文件正文进行三栏合并。

重命名追踪用于历史查询、比较。首版单文件恢复使用所选文件的**历史路径**；不会擅自将旧内容改写到当前新名称。实际新增、覆盖、删除路径在恢复预览中确认。整工程恢复则按所选版本的完整路径布局处理。

### 存储与保留

`.hanshu/service/history/objects/` 按 SHA-256 保存压缩内容，多个版本引用相同内容时只保存一份对象；`revisions/` 保存每个版本的完整 gzip 清单与变化元数据；`labels/` 保存名称。完整清单让任意历史读取与恢复不依赖从第一版逐条重放。首版没有自动过期或裁剪，命名和未命名版本都保留；容量统计包含磁盘上的历史对象和清单。后续可在不改变版本语义的前提下增加索引、清单增量与显式保留策略。

S 在读取文件树、历史及提交前发现的外部磁盘变化会记为「外部修改」，不归到下一位协作者名下。当前没有文件系统监听器，只能记录检查时看到的状态，不能追溯两次检查之间外部工具产生又覆盖掉的中间内容。目录仍应由单个 S 管理。

原剧本工作区的 localStorage 自动快照不再写入。「导出旧本地历史」仅导出当前浏览器中的旧数据，不删除，也不自动混入工程历史。工程历史与本窗口 undo/redo、未提交草稿是不同功能；恢复旧版不会撤销其他版本记录。

## HTTP / WebSocket 协议 v9

认证请求携带 `Authorization: Bearer <session-token>`。WebSocket 在首条消息认证，不在 URL 中携带令牌。

| 路径 | 方法 | 含义 |
| --- | --- | --- |
| `/health` | GET | 协议与存活检查 |
| `/api/sessions` | POST | 凭证登录 `{credential,clientName}` |
| `/api/sessions/current` | DELETE | 登出并撤销写权 |
| `/api/project` | GET | 主体、会话、角色、写权与文件修订计数 |
| `/api/heartbeat` | POST | 续会话与已持有的文件写权 |
| `/api/presence` | POST | `{path:string|null,entryId?:string|null,activity?:"viewing"|"editing"}` 上报焦点和编辑意图，返回 Snapshot；entryId 仅用于皮肤库路径且不影响租约，允许合法的新文件路径 |
| `/api/subjects` | POST | owner 创建主体并签发凭证 |
| `/api/subjects/{id}` | PATCH | owner 改角色或启停主体 |
| `/api/files` | GET | 文件树、各文件/目录的版本 |

| `/api/files/plan` | POST | `{operations:[{op,path,destination?}]}`，查询 S 推导的操作计划；viewer 也可查询 |
| `/api/files/leases` | POST / DELETE | 按传入路径申请/接管、释放写权，不自动展开关系 |
| `/api/files/commit` | POST | `{transactionId,changes:[{op,path,version,leaseId,content?,destination?,destinationVersion?}]}`，返回不可变回执 |
| `/api/files/transactions/{transactionId}` | GET | 查询同一主体的提交回执；不存在为 404，其他主体为 403 |
| `/api/history?before=…&limit=…&path=…` | GET | 按序号倒序分页；可筛选资源及归属资源，支持改名追踪 |
| `/api/history/stats` | GET | 当前历史序号、版本数、对象数、存储大小、命名数 |
| `/api/history/{sequence}/tree?path=…` | GET | 历史文件树；可限定资源范围，`scopePath` 返回该版本对应的旧路径 |
| `/api/history/{sequence}/content?path=…` | GET | 历史文件的 Base64 内容、大小和摘要 |
| `/api/history/{sequence}/label` | POST | `{label:string\|null}` 设置或清除准确版本的名称 |
| `/api/history/restore-plan` | POST | `{sequence,paths:string[]\|null,skinEntryId:string\|null,includeRelated}`；返回待确认的恢复计划，`paths:null` 表示整工程 |
| `/api/events` | WebSocket | 当前状态与后续通知 |

操作为 `write/mkdir/remove/move/check/skin-entry-patch/skin-library-command/history-restore`，正文使用 Base64，普通文件操作的 `version:null` 表示原来不存在。`check` 只验证路径版本和写权，不改内容。回执为 `{transactionId,status,tree,error,skinEntries?,skinCommandResult?}`：`status=committed` 带原提交时的文件树，`status=rejected` 带确定拒绝原因。认证或存储未恢复等仍可能返回 HTTP 错误，C 不能把网络断开当作提交失败。旧 `/api/resources` 和 `/api/files/source-plan` 入口已移除；v9 需要 C/S 一起更新。类型由 Rust 生成到 `src/collab/generated.ts`。

`history-restore` 必须是独立的一笔 `/api/files/commit`，路径固定为 `project.json`，`version:null`、`leaseId:""`，正文为预览返回的 `request` 的 Base64 JSON（含 `expectedHead`），不能混入其他操作。路径只是命令入口，S 从已授权的历史和当前资源关系生成实际动作、校验版本并取得临时写权；不会把请求正文写进工程清单。

`skin-entry-patch` 仅允许路径 `.hanshu/skinmanager/library.json`，正文为 `{entryId,expectedRevision,changes}` 的 Base64 JSON。`changes` 白名单为名称、标签、收藏、位置、启用、模型、协议、来源、备注和自定义 ID，不接受对象身份、条目身份、修订号等替换。它按条目修订号校验而不比较索引文件哈希；S 继续校验角色、短期索引写权、文件夹存在、自定义 ID 唯一和最终对象引用。成功回执的 `skinEntries` 保存该次确认的条目，重放不重新执行或返回后来版本。

`skin-library-command` 使用同一固定路径，正文为带 `command` 字段的 Base64 JSON。命令包括 `ensure-library/import-entry/batch-patch/delete-entries/create-folder/patch-folder/delete-folder/rename-tag/delete-tag/delete-folder-entries`。条目操作使用 `expectedEntries:[{entryId,revision}]`，文件夹操作使用 `expectedFolder`，范围操作额外携带完整的条目或文件夹快照。S 在最新索引上执行命令并返回 `skinCommandResult`；请求、结果、落盘和回执归档继续使用同一文件事务机制。一笔事务最多包含一个皮肤语义操作，可与必要对象写入合批；不能夹带第二个命令或再次直接覆盖索引。业务实现入口为 `project-core/src/skin_commands.rs`，C 请求类型位于 `src/skin/local/libraryCommands.ts`。

操作计划请求上限 256 KiB，原始请求和展开后的动作各不超过 4096 项。计划查询不刷新客户端草稿基线；结果未知的事务在计划查询失败时也必须保留原提交编号，直到查询到明确回执。

`Session.filePresence` 为 `{path,authorityId,entryId,activity}` 或 `null`，普通文件的 `entryId` 为 `null`，皮肤条目使用其条目 ID。自由编辑器的 `activity` 为经 S 权限校验的编辑意图；进度及其所属资源仍根据实际写权推导 `viewing/editing`。查看、编辑意图和条目 ID 均不会申请写权。普通心跳不改变文件焦点。Snapshot 的 `statusVersion` 是单次服务运行中递增的状态序号，C 丢弃比已收到版本更旧的 HTTP/WS 快照，避免迟到心跳恢复已经丢失的写权。`serverTime` 用于在 C 以单调时钟估算租约剩余时间，不要求两台设备的系统时钟一致。服务重启后旧会话失效，重新登录建立新的排序作用域。

## 验证与当前限制

2026-10-22 验证包括 Rust 权限、目录事务、持久回执和崩溃恢复，C 的事务队列与编辑器边界，真实 HTTP/WebSocket 多会话，隔离浏览器的多文件冲突处理，以及前端构建、协议生成一致性与桌面 Rust 编译。网络验收使用本机 Ethernet IPv4 和普通 HTTP，经过故障代理注入延迟、断线及提交成功后的截断响应，验证重新登录／刷新后的结果查询、重复移动／删除、服务重启、进度与流程图创建和皮肤导入。测试中没有授予 C 直接工程文件系统写入能力。

环境只有一台可用物理设备，未配置可访问的第二台主机。不同浏览器上下文和真实网卡地址覆盖了网络协议与协同路径，但不等于两台物理设备验收，也未验证跨设备防火墙和路由配置。可复现脚本为 `scripts/verify-collaboration-network.mjs`，生成 `../output/collaboration-network/acceptance.json` 和截图。

统一协作栏另由 `scripts/verify-unified-presence.mjs` 在三个隔离浏览器上下文中覆盖 10 组交互：剧本与流程图编辑状态、进度互斥写权、皮肤条目范围、现场失败恢复、成功回复丢失、弹窗原操作确认、断线重连、工作区焦点切换和窄窗口布局。结果及截图在 `../output/unified-presence/`。`scripts/verify-presence-ui.mjs` 的原有进度验收 7 组也已通过，包括接管、断线和降权后保留草稿。两套均使用真实 HTTP/WebSocket，仍只覆盖一台物理设备。

工程历史另有 `scripts/verify-project-history.mjs` 的 15 组真实 HTTP 验收，以及 `scripts/verify-project-history-ui.mjs` 的 6 组浏览器验收。覆盖三个独立客户端、命名与对比、源文件及语言的关联历史、丢失成功回复后的原事务查询、过期预览、单皮肤恢复、跨工程隔离、服务重启和窄屏界面；浏览器测试没有 pageerror。报告和截图在 `../output/project-history/`。Rust 另覆盖提交决议崩溃恢复、损坏对象拒绝、历史分组、恢复权限，以及文件和目录类型替换及其回滚。仍未进行第二台物理设备验收。

首版单个文件上限 32 MiB、工程 256 MiB / 16384 个文件和目录，批量事务最多 4096 项，网络请求正文上限 48 MiB。文件树使用内存扫描和串行提交，面向小规模工程；后续可优化索引和存储，不改变 C 无直接工程写入能力的边界。服务运行时应通过 S 编辑工程；外部改盘在读取或提交检查时记录，不是实时文件监听。

持久回执采用有限热缓存和永久磁盘归档，不再因累计 1,024 条或 128 MiB 而停止接收新提交。热缓存最多 64 条，序列化 JSON 大小合计不超过 8 MiB；这是缓存计量，不是整个服务的内存上限。较大回执直接从磁盘读取。每份完整回执保存在 `.hanshu/service/file-transactions/archive/<事务编号 SHA256 前两位>/<完整 SHA256>.json.gz`，保留主体、请求摘要和原始结果。缓存淘汰不删除归档，也不会将旧编号视为新提交。单份解压 JSON 最大 128 MiB，超过时在修改工程文件之前拒绝该次提交。

启动时逐份解压校验归档并恢复 revision，常驻缓存有界，但启动时间随历史增长；尚未实现启动索引、归档管理界面或磁盘空间预警。旧平铺 JSON 回执会逐份转换，先原子写入并校验归档，再删除旧副本；中断留下的两个副本必须完全一致。归档不会自动过期或删除，总磁盘占用会持续增长。备份应包含完整 `.hanshu/service`，不要手动清理回执文件，否则会丢失对应提交的幂等依据。归档读取失败或损坏不会被当作“没有此回执”；未完成的提交决议仍需恢复后才能继续文件操作。

窗口关闭后旧会话写权随 30 秒租期到期；管理者可以显式接管，重新登录不会隐式夺取其他会话的写权。

资产缓存退出清理只触及当前运行实例，并保留 BFCache 内页面；崩溃残留缓存暂不跨窗口自动清理，避免误删休眠中的客户端。资产缓存属于可重建投影，重新加载页面会从 S 加载，再恢复语言草稿和持久事务。
