# 工程服务与多人协作

React 是 C，Rust 工程服务是 S。连接 S 就是打开一个完整工程，剧本、进度、流程图、脚本、物品、礼包、导航器、资产与皮肤工作区使用同一工程会话。原来的独立「共享进度」入口已移除。

## 权威边界

- S 持有普通工程目录，维护主体、会话、授权、写权与文件版本。所有工程创建、保存、覆盖、改名、移动和删除都由 S 执行。
- C 不持有工程目录的 OS 文件系统句柄。`ProjectDirectory` 是只读的远程目录引用，不含 `createWritable`、`removeEntry` 或任意本机路径打开能力。写入通过明确的 HTTP 工程命令请求。
- 浏览器本地存储、IndexedDB 是草稿与缓存，不能直接覆盖服务端工程。资产缓存按页面运行实例隔离，同窗口工作区共享；同浏览器多个标签页不会互相读写未保存草稿。文件导入只读取用户选择的文件；导出下载到客户端，不能指定服务端绝对路径。
- 桌面版运行同一 S。选择本机工程目录的对话框由可信的 Rust 宿主弹出，返回服务连接信息；C 不获得目录写权限。旧皮肤库写入 IPC 与 WebView 文件读写自动授权已移除，原生网络辅助仍可用于下载皮肤。

## 主体、会话与授权

Subject 是身份主体，包含 `id/name/kind/enabled`，可表示自然人、agent、服务或工具。凭证登录建立 Session；同一主体打开两个客户端，会得到两个独立会话。

工程角色为 owner/editor/viewer。owner 创建主体、调整授权、停用主体和接管写权；editor 修改资源；viewer 读取资源。权限由 S 检查，绕过界面直接请求也不会获得写入能力。目前采用管理者签发的高熵凭证，不提供密码注册、密码找回或第三方登录。以后可增加认证入口，继续复用同一主体与工程授权。

会话令牌只保存在内存，不写 URL 或持久化浏览器存储。会话有效期 60 秒，客户端每 8 秒心跳；服务重启后重新登录。管理者恢复凭证仅位于 S 的私有目录，HTTP 不返回它；新主体凭证仅创建时返回一次。

## 工程目录

```text
工程根/
  project.json                 # 原工程清单，不是服务身份数据库
  src/                         # .hs/.char/.py/.progress/.hflow/.nav/.item/.kit
  meta/                        # 创作资料与配音服务配置
  assets/                      # 语言、图片、音频等
  .hanshu/
    skinmanager/               # 皮肤集合与对象文件
    service/                   # S 私有状态，不经资源 API 暴露
      project.json             # 主体、授权、凭证哈希
      owner-key
      service.lock
      file-undo.json           # 事务期间存在的撤销记录与提交决议
      file-transactions/       # 按主体隔离的不可变提交回执
      write-staging/           # 私有原子替换暂存区
```

S 打开普通工程目录，直接读写这些资源，不需要把进度文件另外导入一份独立数据库。原型第一版的独立协作数据库不作为普通目录工程自动兼容。

仅允许访问工程清单、`src`、`meta`、`assets`、`.hanshu/skinmanager`。S 拒绝绝对路径、`..`、Windows 设备名/ADS、大小写冲突、符号链接/目录联接，以及服务私有目录。工程目录同时只能由一个 S 进程管理。

## 修改与一致性

每个文件的版本是其内容哈希，目录版本包含整个子树。C 提交读取时的版本，S 同时验证会话、权限、写权与版本；409/423 不会自动改用新版本重试覆盖。

写权属于会话，30 秒有效并随心跳续租。第一次提交某个资源时申请写权，界面可查看持有者、释放全部写权，管理者可接管。不同资源可由不同会话同时持有；同一资源的未提交本地编辑仍是草稿，只有有效写权持有者能提交。

源文件及其语言、配音资源共用源文档写权，防止两个人分别修改 `.progress` 和它的标题语言文件。S 为改名/删除推导完整关联资源列表，并检查事务包含全部关联项。目录操作也检查子树中的写权。

文件事务先校验整批修改，再保存撤销日志、执行原子文件替换，最后持久化提交决议和回执。执行失败尝试回滚；没有提交决议的日志在重启时回滚，有提交决议的日志只补全回执，不重复移动或删除。恢复失败则拒绝继续提供文件操作。临时替换文件位于 S 私有目录，不进入工程资源树。逐文件原子替换与恢复日志保护的是经 S 访问的工程，不向绕过 S 的磁盘读取程序承诺跨文件原子视图；当前测试覆盖进程中断恢复，没有宣称硬件断电下的全盘持久性保证。

保存只提交变更，不根据客户端清单中缺少的条目删除文件，也不整树删除后重写 `assets`。删除是显式命令。`.progress` 执行结构校验，皮肤库索引检查基本结构；普通源码可以保留未完成内容，S 不执行目标定义或游戏脚本。

### 客户端编辑事务

C 的 `EditTransactions` 协调一次操作的变更集，不增加“逻辑文档”或资源归属模型。编辑器决定哪些文件必须一起修改，S 继续负责写权、版本校验和批量落盘。外链共享资源只在实际被修改时进入变更集，不因为被引用就自动加入。

剧本与进度编辑器中的语言修改先暂存为草稿，不再单独自动提交。Ctrl+S 或全局「保存修改」等待语言缓存写入及资源登记完成，收集当前工程的全部已修改正文、语言和资产，再发送一个批量事务。收集期间若继续编辑，重新收集以避免正文和语言来自不同草稿时刻；提交期间产生的新草稿保留为下一次待保存内容。不同路径的本地语言镜像可独立准备，同一路径按顺序写入，准备失败则不发送这次保存。

工程栏显示待保存、准备、提交、失败与冲突，并提供提交记录、原提交重试和提交备份导出。失败记录保留原内容和原版本；重试不会重新收集新输入或采用远端最新版本覆盖。相关路径存在未处理失败时，不允许另一提交绕过它，不相关资源仍可提交。「移除记录，保留草稿」只移除确定失败的记录，不改变草稿和版本；未知结果必须先查询，不能直接移除。

每次发送前，将完整修改快照（包括二进制）、原版本和 `transactionId` 保存到 IndexedDB。存储失败则不发送。回执按主体绑定，不绑定旧会话；重新登录后仍能查询自己的结果。确定拒绝后的重试使用新编号，结果未知时保留原编号和原请求内容，先查询回执再决定是否重发。仅 leaseId 可随新会话变化。原编号用于不同内容时 S 拒绝。点击「查询提交结果」只查询，点击「重试原提交」在没有回执时可重发同一请求。S 已提交的移动、删除不会重复执行。

版本冲突提供三栏对照：原始版本、服务器版本、本次提交内容。每个资源可采用服务器版本或保留本地修改，文本写入还可手动合并。移动和目标写入作为一个联动决定。提交处理结果时，所有修改仍是一批；采用服务器的路径转换为 `check`，与写入一起校验版本。对话框打开后服务器再次变化，整批拒绝，需重新载入版本再处理。二进制不尝试文本合并，可导出原提交备份。结果确认后更新缓存与各编辑器；确认期间产生的新草稿保留，历史回执也不会覆盖他人随后提交的新版本。

改名/删除之前若该源文件还有暂存的语言修改，先要求保存，避免草稿在旧路径被重新创建。其他资源操作经 `ProjectClient.apply` 进入同一事务队列和状态记录；具体编辑器仍需显式把业务上不可分开的修改组成一个批次，并非相邻的多次调用自动合并。

配音替换把 `.ogg` 写入和同键 `.ref` 删除组成一批；批量设置引用、批量删除各自组成一批。剧本与进度多选改名／删除先由 S 推导所有关联项，再整批执行。皮肤索引修改串行化，导入对象与索引一起保存；垃圾清理带索引版本检查。上述操作在 S 确认后才改变本地资源列表，重试成功也会补做本地投影。多键音频导入、TTS 和批量皮肤导入按条目提交，允许取消和部分成功，每个条目内部原子化。普通资产导入仍是草稿，随工程保存。

开发入口为 `src/project/editTransactions.ts`。`stageWrite(edit, prepare)` 暂存文件及其异步本地镜像；`submit(label, collect, true)` 等待准备并合并暂存修改；独立操作使用 `ProjectClient.apply(edits, label)` 显式提交一批文件。`npm run test:edit-transactions` 验证准备失败、收集时继续编辑、提交时继续编辑、原版本重试和语言合批。

WebSocket 通知文件版本与主体/写权状态，不广播全部正文。C 按版本读取变化，更新未修改的资源，保留本地修改。窗口内的源文件正文和暂存语言草稿保存在 sessionStorage，并携带原版本；重连不会把旧草稿自动覆盖到 S。待处理事务及其完整二进制快照持久保存在 IndexedDB，作用域为工程 ID、主体 ID 和窗口 ID；刷新同一窗口并重连会恢复。恢复不会自动提交。会话令牌不进入日志。尚未开始提交的二进制修改仍属于缓存草稿；尚无提交备份自动导入入口。清除浏览器站点数据会删除本地草稿和待处理记录；可通过「导出此提交」另存备份。

## 开发与本机使用

```sh
npm install
npm run dev
```

同时启动 Vite（`http://localhost:5173`）和 Rust S（`127.0.0.1:47831`）。默认工程目录 `.hanshu-project/`，管理者凭证 `.hanshu-project/.hanshu/service/owner-key`；用 `HANSHU_PROJECT_DIR` 指定已有工程。点击全局「打开工程…」，服务地址默认 `/__project`，填入凭证和本端名称。空目录第一次打开时可填写工程名称。

`npm run dev:ui` 仅启动 C；`npm run server` 仅启动 S。Rust 源码修改后开发服务重编译/重启，需重新登录，窗口源文件草稿可恢复。

`npm run desktop:dev` 启动桌面壳与内置 S，默认目录为应用本地数据目录的 `projects/default`，经本地 IPC 自动登录。打开窗口中的「由本机服务打开文件夹…」可以选择普通工程；也可输入远端服务地址与凭证。

## 局域网中心服务

```sh
npm run build
cargo run --manifest-path src-tauri/Cargo.toml -p project-server -- --project /path/to/project --listen 0.0.0.0:47831 --origin http://192.168.1.10:47831 --web-root dist
```

替换目录和中心设备 IP，放行相应防火墙端口。其他设备访问 `http://192.168.1.10:47831`，使用各自主体凭证打开工程。`--origin` 可重复指定；C 单独部署时填写其页面来源。`--web-root` 可省略，此时只提供 API。静态目录不能包含工程及凭证目录。

首版不内置 TLS、互联网穿透、跨项目目录浏览或多服务器复制。公网部署需另外配置加密接入。多人同步以文件写权和版本校验为基础，还没有 `.hs` 或节点图操作级的共同编辑。

## 手工验收路径

1. 用两个浏览器窗口或同一浏览器的两个标签页打开同一个工程，分别登录编辑主体。打开同一份进度。
2. A 修改标题但不保存；B 修改完成方式并保存。服务器标题应保持原值，A 的未保存标题应仍在 A 窗口里。B 释放写权后，A 可以提交自己的修改。
3. 让两端都先修改正文和标题，A 保存并释放写权，再由 B 保存。B 的版本冲突记录应提供「处理冲突」；对比三栏后，可将一份资源采用服务器，另一份手动合并，再一次提交。
4. 在 B 处理冲突期间，用 A 再保存被 B 采用的资源。B 提交应整批拒绝，另一份资源不得先写入；重新载入服务器版本后才能继续处理。
5. 使用下方网络脚本复现截断响应、重新登录、刷新和重复移动／删除。未知结果记录应允许查询，原提交编号保持不变；服务已完成的操作不会重复执行。
6. 复制一个仍有待确认提交的标签页：复制页应取得独立的提交记录作用域，原页刷新后仍可查询原记录。普通标题和语言草稿可以被浏览器复制为独立草稿，但两个页面的后续缓存写入互不影响。

## HTTP / WebSocket 协议 v3

认证请求携带 `Authorization: Bearer <session-token>`。WebSocket 在首条消息认证，不在 URL 中携带令牌。

| 路径 | 方法 | 含义 |
| --- | --- | --- |
| `/health` | GET | 协议与存活检查 |
| `/api/sessions` | POST | 凭证登录 `{credential,clientName}` |
| `/api/sessions/current` | DELETE | 登出并撤销写权 |
| `/api/project` | GET | 主体、会话、角色、写权与文件修订计数 |
| `/api/heartbeat` | POST | 续会话与已持有的文件写权 |
| `/api/subjects` | POST | owner 创建主体并签发凭证 |
| `/api/subjects/{id}` | PATCH | owner 改角色或启停主体 |
| `/api/files` | GET | 文件树、各文件/目录的版本 |
| `/api/files/content?path=…&version=…` | GET | 读取文件；可要求特定版本 |
| `/api/files/source-plan?path=…&destination=…` | GET | S 推导源文件操作及关联项 |
| `/api/files/leases` | POST / DELETE | 申请/接管、释放写权 |
| `/api/files/commit` | POST | `{transactionId,changes:[{op,path,version,leaseId,content?,destination?,destinationVersion?}]}`，返回不可变回执 |
| `/api/files/transactions/{transactionId}` | GET | 查询同一主体的提交回执；不存在为 404，其他主体为 403 |
| `/api/events` | WebSocket | 当前状态与后续通知 |

操作为 `write/mkdir/remove/move/check`，正文使用 Base64，`version:null` 表示原来不存在。`check` 只验证路径版本和写权，不改内容。回执为 `{transactionId,status,tree,error}`：`status=committed` 带原提交时的文件树，`status=rejected` 带确定拒绝原因。认证、容量限制或存储未恢复等仍可能返回 HTTP 错误，C 不能把网络断开当作提交失败。旧 `/api/resources` 入口已移除。类型由 Rust 生成到 `src/collab/generated.ts`。

## 验证与当前限制

2026-10-22 验证包括 Rust 权限、目录事务、持久回执和崩溃恢复，C 的事务队列与编辑器边界，真实 HTTP/WebSocket 多会话，隔离浏览器的多文件冲突处理，以及前端构建、协议生成一致性与桌面 Rust 编译。网络验收使用本机 Ethernet IPv4 和普通 HTTP，经过故障代理注入延迟、断线及提交成功后的截断响应，验证重新登录／刷新后的结果查询、重复移动／删除、服务重启、进度与流程图创建和皮肤导入。测试中没有授予 C 直接工程文件系统写入能力。

环境只有一台可用物理设备，未配置可访问的第二台主机。不同浏览器上下文和真实网卡地址覆盖了网络协议与协同路径，但不等于两台物理设备验收，也未验证跨设备防火墙和路由配置。可复现脚本为 `scripts/verify-collaboration-network.mjs`，生成 `../output/collaboration-network/acceptance.json` 和截图。

```sh
cargo test --manifest-path src-tauri/Cargo.toml -p project-core
cargo build --manifest-path src-tauri/Cargo.toml -p project-server
npm run check:protocol
npm run test:project-boundary
npm run test:edit-transactions
npm run test:editor-transactions
npm run test:project-crypto
npm run test:collaboration
npm run build
npm run test:collaboration:ui
npm run test:collaboration:network
npm run test:asset-cache-isolation
npm run test:edit-journal
```

首版单个文件上限 32 MiB、工程 256 MiB / 16384 个文件和目录，批量事务最多 4096 项，网络请求正文上限 48 MiB。文件树使用内存扫描和串行提交，面向小规模工程；后续可优化索引和存储，不改变 C 无直接工程写入能力的边界。服务运行时应通过 S 编辑工程，暂不监听外部工具的磁盘修改。

持久回执目前最多 1,024 条或 128 MiB，达到任一上限后拒绝新提交，已有回执仍可查询和重放。尚无回执归档或管理界面；不会静默淘汰回执后把旧编号当作新提交。窗口关闭后旧会话写权随 30 秒租期到期；管理者可以显式接管，重新登录不会隐式夺取其他会话的写权。

资产缓存退出清理只触及当前运行实例，并保留 BFCache 内页面；崩溃残留缓存暂不跨窗口自动清理，避免误删休眠中的客户端。资产缓存属于可重建投影，重新加载页面会从 S 加载，再恢复语言草稿和持久事务。
