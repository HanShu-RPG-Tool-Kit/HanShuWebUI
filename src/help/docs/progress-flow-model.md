# 多进度任务（树图）模型

本文描述游戏性工作区中**多进度**作者态的模型语义：一层节点、信号方向、以及与引擎的边界。文件为 **`.quest`**（`format: "hanshu.progress-tree"`）。单进度表单见 [任务文档](#progress-document)；节点、端口、信号的逐项实现参考见 [多进度节点图](#progress-node-graph)；画布操作用法见 [游戏性工作区](#gameplay-workspace)。

## 1. 模型定位

| 层 | 职责 |
|----|------|
| **进度图** | 进度节点（阶段）+ 目标节点（后台 goal）+ 逻辑 + 条件 + 结束；文档 `hanshu.progress-tree` v1 |
| **运行时** | A（顺流激活）/ Q（逆流查询）/ C（逆流取消）/ N（否定应答）；进度、目标、条件各自持有生命周期状态 |
| **校验** | 端口、连线、目标结构、进度标识符唯一性；画布成环是 error |

进度承载阶段内的 `goals[]` 与 `completion`；目标节点承载单个 Quest 级后台 goal，随任务启动、不进入任务 UI 跟踪。goal 执行与累计值由实例负责，图模拟器只手动注入成功/失败结算并验证信号。逻辑只做「组合判断、放行、转发取消」，条件持续提供当前条件真值，结束节点锁存 quest 唯一终局并终止传播，剩余队列不再投递。

## 2. 文档结构（摘要）

```json
{
  "format": "hanshu.progress-tree",
  "version": 1,
  "id": "a-stable-document-id",
  "start": "progress_start",
  "progress": {
    "progress_start": {
      "identifier": "start",
      "questTitle": { "text": "progress.progress_start.questTitle" },
      "description": { "text": "progress.progress_start.description" },
      "runningLog": { "text": "progress.progress_start.runningLog" },
      "completedLog": { "text": "progress.progress_start.completedLog" },
      "goals": [],
      "completion": "all"
    }
  },
  "predicates": {},
  "objectives": { "background_goal": { "goal": { "kind": "", "params": {} } } },
  "transitions": {},
  "ends": {},
  "logic": { "links": [] },
  "layout": { "positions": {}, "notes": {}, "groups": {} }
}
```

解析只接受当前结构：旧集合 `entry` / `nodes` / `goals` / `conditionals` / `diffs` / `merges` / `swaps`、根级 `name` / `description` / `title` / `kind`、逻辑节点带内容，一律视为非法，不做迁移。

当前 v1 的旧进度 `title` 读取时归一为 `identifier`，重复值自动加后缀；旧条件 `title` 被移除。进度标识符是普通字符串，不是本地化键；包括开始节点和草稿节点在内，在同一 quest 中必须唯一、非空、无首尾空白、不含换行或制表符且不超过 200 字符（区分大小写）。节点内部 ID 仍负责连线引用，修改标识符不会断开连线。任务标题 `questTitle`、任务说明、日志和结局标题仍使用可本地化的 `FlowText`。

## 3. 节点语义

| 节点 | 内容与语义 |
|---|---|
| **开始进度** | 唯一；没有左端口，任务开始时直接进入运行中；有两个右端口（成功 / 失败）；承载 `questTitle` 与 `description` |
| **进度** | 阶段。`identifier` / `runningLog` / `completedLog` / `goals` / `completion`（含 `custom`）；A 进入 → 运行中并向左端口发 C（消费输入）；结算 → 已成功 / 已失败并按端口发 A；Q 按结局回报 A / N；C 在运行中使其已取消、未激活时向上游转发 |
| **条件** | 可选非本地化标识符，无标题、无左端口；未激活 / 运行中 / 已关闭；运行中按 `conditions` 判断，空条件恒假；上升沿发 A，Q 按当前真值回 A / N；C 关闭整个节点，之后 Q 回 N |
| **目标** | `objectives`；必填非本地化标识符、单个 `goal`、可选节点级提交方式；无左端口、成功/失败两个右端口；未激活 / 运行中 / 已成功 / 已失败 / 已关闭。实例结算进入成功或失败并按口发 A；配置提交时仅实际提交成功才成功。C 关闭整个节点，之后两个口 Q 都回 N。不跟踪任务 UI，不维持任务存活 |
| **逻辑** | 左端口分「并且」（全部 A）与「或者」（任一 A）；收到 A 开一轮 Q，满足才放行，不主动产生 C；收到 C 仅向输入转发；收到下游 Q 则独立递归查询输入，只沿原请求回复 A/N，不放行、不消费；空输入查询回 N |
| **结束** | 成功入 / 失败入；进入即记录任务终局；`title` 与 `rewardKits`；可以有多个 |

状态只存在于模拟器：进度五态，逻辑只有一轮查询的临时簿记。

进度（含开始进度）与目标统一使用可选 `submission: {submit_type, param}`：UI 为 `{submit_type:"ui", param:null}`，对话注入点为 `{submit_type:"dialogue_injection", param:"quest_submit"}`，不带 `@`，类型与参数均不本地化。进度只配置一次，提交时提交其全部 goal；内嵌 goal 不描述提交。缺省表示无需提交；交付型 goal 必须在所属节点上配置入口，详见[多进度节点图](#progress-node-graph)的统一提交格式。

**连接约束只有一条**：右端口 → 左端口，且不能成环（含自环）。与开始进度节点**联通**（连线视为无向）的节点是生效节点，其余是草稿节点。

**终局兜底约定**：任务已开始、尚无终局且没有执行故障时，每轮信号全部结算后，若没有运行中的进度，或所有运行中的进度都无法沿业务连线正向到达任意结束节点的成功入或失败入，则任务自动失败。条件未来可能变真不推迟判定，自动失败后也不能靠条件恢复。这里检查的是有向结构可达性，与草稿节点的无向联通判定不同；暂停和断点不算结算完成。

目标同样不能延长存活，即使仍运行且有结束出路，也不等待未来结算。开始进度与生效目标、条件先一起初始化，再处理启动信号，最后检查结算边界。目标的成功、失败属于生命周期终态；C 将条件、目标整体关闭，不只是关闭某条连线。重置以外不重新打开。提交声明与配置契约见[多进度节点图](#progress-node-graph) §2.3.1。

没有结束节点是合法语法，但任务开始后会在首次结算边界失败。进度的成功口和失败口都无出连线也合法，其结算不会直接触发结局；激活时的上游消费规则仍然有效。完整时机、失败效果和例外见[多进度节点图](#progress-node-graph) §9.4。模拟器已执行该自动失败契约。

**编辑**：双击节点在画布上打开表单视图（每个节点最多一张，会话内有效）；可将表单或其中的日志、完成节点编辑器放大到弹窗中编辑。

## 4. 设计取舍

- **成功与失败是端口，不是第三种信号**：边从哪个口离开就代表哪种结局，画布上直接可见。
- **Q 让边成为电平触发**：新激活的逻辑可以追问已有节点，读到「已经成功过」的事实；没有 Q，只能等边沿。
- **C 逆流 = 消费/互斥**：只有普通进度收到 A 从未激活进入运行中时，才主动向自己的输入端口发 C；逻辑与未激活进度只转发收到的 C——「这个消费者不要你了」。仍在运行的上游会被取消，已结算 / 已取消的忽略；同一端口多候选上游时先到者赢。
- **逻辑放行后重复收到 A 不会重复推进**：下游进度只接受未激活时的 A，天然幂等；真相机里这是「消费一次」。
- **旧模型的差分逻辑、合并逻辑、交换逻辑不再需要**：差分被进度的双出口取代，合并被并且 / 或者端口取代，交换被「下游进度激活后消费上游」取代。
- **条件事实与生命周期分开**：运行中才监听真值，在初始化时广播一次已为真者，之后只在假→真的上升沿增量广播；C 关闭整个节点，停止监听和广播，后续 Q 回 N。共享节点一旦被任一消费者关闭，其他消费者也不能继续查询真值，需显式考虑共享分支的消费关系。
- **跨任务依赖**：条件节点的判断规则可以引用别的任务状态，引擎必须在所有实例状态加载完之后再统一初始化并广播。
- **传播是 FIFO 队列**：每个投递立刻完成自己的状态变化，产生的信号追加到队尾；端口的持久 `order` / `reverseOrder` 与外部结算顺序参与结果；数组重排不影响运行。具体规则见[多进度节点图](#progress-node-graph)的「信号处理顺序」。

## 5. 表达能力的当前边界

已具备：链式推进、成败分叉、并且门（全部满足）、或者门（任一满足）、条件门、汇合后再放行、互斥（先到者取消其余）、任务成功 / 失败终局。

尚未接入：进度内的 goal 自动判定与 `completion` 策略、条件表达式、外部激活（对话 / 事件 key）、竞速裁决、多令牌实例身份、导出时剥离 `layout`。

## 6. 扩展设想：进度弃用（暂无计划实现）

**状态：仅记录讨论，暂无计划实现；不是当前运行契约，也不是已排期功能。** 当前文档格式、编辑器与模拟器均未提供进度弃用能力。

背景是模板更新后，如何保留已运行实例正在经历的旧进度，同时停止让后续流程进入它。曾讨论将「弃用」设计为模板属性而非新的运行状态：

- 弃用进度忽略 A，不再从未激活进入运行中。
- 已运行的弃用进度仍可照常成功或失败，并从对应右端口发 A。
- C 沿用普通进度规则：运行中变已取消，未激活时向上游转发，已结算时忽略；Q 仍按状态及查询端口应答。
- 运行中的弃用进度仍按现有规则参与任务存活判定；弃用本身不取消、不结算、不发信号。
- 编辑器可选择隐藏弃用节点；隐藏仅影响视图，不删除节点、连线或实例状态。

暂不推进的原因是它会增加作者理解激活、取消、任务存活及模板更新之间关系的负担，而且单独的弃用标记不能保证旧实例迁移安全。若将来重新评估，仍需明确开始进度能否弃用、结构可达性是否穿过未激活的弃用节点，以及旧实例所需 goal 与连线如何保留；这些边界**尚未定案**，不能视为已确认规则。

- 结构与校验：`src/workspaces/gameplay/model.ts`

模拟器支持待投递队列、逐条单步、播放/暂停、速度与沿线动画。终局 first-wins 并清空队列；预算故障回退整次事件。完整排序、规模限制与故障约定见[多进度节点图](#progress-node-graph)。
